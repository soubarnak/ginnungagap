# S-02: launch latency of a command in a running realm

Risk R-006, requirement NFR-004 (p95 <= 300 ms from launcher invocation to process start in the realm). Also checks NFR-005 and FR-017 (cold start) and FR-046 (exported app launch path).

**Verdict: S-02: PASS** against p95 <= 300 ms on the `podman exec` path (two full runs: p95 136.0 ms and 211.8 ms). The C helper meets the latency but fails the parity check in section 4, so it is not recommended for the launch path.

## 1. Environment

- Host: Void Linux (glibc), kernel 7.2.9_1, AMD Ryzen 5 7535HS, 15 GiB RAM (about 1 GiB available at session start, about 6 GiB during the runs), 8 GiB swap.
- podman 5.8.8 (rootless), runc 1.5.2, cgroup v2, cgroupfs cgroup manager, overlay storage.
- Python 3.14.8 at `/usr/sbin/python3`.
- Dedicated storage: `--root ~/.local/share/ginn-spike-s02/podman --runroot $XDG_RUNTIME_DIR/ginn-spike-s02`. Reset at the end of the spike.
- Image: `docker.io/library/alpine:3`.
- catatonit is absent from `/usr/bin` and `/usr/libexec/podman`. The container therefore runs without `--init`. Host Setup or packaging must supply catatonit for FR-082.
- Host noise: run 1 started at load average 7.1 with io pressure avg10 near 50 percent. Run 2 started at load average 1.8 with io pressure avg10 near 46 percent.

## 2. Method

- Script: `spikes/s02_launch_latency.sh`. It builds `spikes/out/s02_run` with `cc -std=c11 -O2 -Wall -Wextra -Werror` and runs every measurement.
- Timer: `python3 -I` with `time.perf_counter_ns` around `subprocess.run`, stdin from /dev/null. Each return code is checked. Any nonzero return aborts the run.
- Warm-up: 5 calls discarded per row. 100 calls measured. Percentiles use the nearest-rank method.
- Cold path (FR-017, NFR-005): `podman stop -t 0` and the state check are untimed. `podman start` is timed. 2 warm-up cycles discarded, 20 measured.
- Two full runs of the script were made. Both are reported.

## 3. Gates, run before any timing

- For `podman exec`, `s02_run` and `nsenter`: the process sees the Alpine rootfs, runs as uid 1000, has a small in-namespace PID, and `sh -c 'exit 7'` returns 7 (IR-011, FR-049 AC-1).
- Negative control: `s02_run 1 true` (host PID 1, root-owned) fails at `open /proc/1/ns/user` with EACCES (errno 13) and exits 125.

## 5. setns findings

- The helper joins `user`, `mnt`, `uts`, `ipc`, `pid`, `cgroup` in that order. It joins `net` only when the inode differs from the host. With `--network host` it is the same inode, so `net` is skipped.
- All six `setns` calls succeeded for the unprivileged owner (uid 1000). No host CAP_SYS_ADMIN was needed. The container's user namespace is owned by the caller's uid, so the caller holds capabilities inside it. This matches the prediction.
- No setns errno was seen on this host. The `nsenter` fallback was not needed. It was run only as a reference and also succeeded.
- The negative control gives EACCES on opening `/proc/1/ns/user`, because PID 1 is root-owned and the ptrace read check fails.

## 6. Parity: what the launched process inherits

Captured from inside each runner with the same script (`/proc/$$/status`, `/proc/$$/cgroup`, `readlink /proc/$$/ns/*`).

| Field | podman exec | s02_run | nsenter (spec flags, no -C) |
|---|---|---|---|
| Uid | 1000 (all four ids) | 1000 | 1000 |
| Groups | 1000 | none (setgroups 0) | 14 x 65534 plus 1000 (unmapped host groups) |
| CapEff | 0 | 0 | 0 |
| CapBnd | 0x00000000800405fb | 0x000001ffffffffff | 0x000001ffffffffff |
| NoNewPrivs | 0 | 0 | 0 |
| Seccomp | 2 (filter active) | 0 (no filter) | 0 (no filter) |
| user, mnt, pid, uts, ipc, net | same inode as container | same | same |
| cgroup ns | joined | joined | not joined |

Consequences for the realm model:

- A helper-launched app runs without the container's seccomp filter. This breaks the syscall restriction that FR-061 and NFR-SEC-002 rely on.
- The bounding set is full, so a binary with file capabilities could gain capabilities the realm tier does not grant.
- Supplementary groups differ. The `nsenter` path also leaks unmapped host groups as 65534.
- Cgroup: the helper child shares host cgroup `0::/2` with the container init, and `podman top` lists it. This does not prove membership. On this host the cgroupfs manager places the container in the caller's cgroup, and the calling shell is also in `0::/2`. Under `--cgroup-parent /ginn/<uid>/<realm>` (ADR-003, M7), a child launched from another cgroup would be expected to sit outside the realm cgroup. That is not tested here.

Any helper path would need the same seccomp filter, bounding set, group reset and cgroup placement as `podman exec` before it could be used.

## 7. Recommendation for ADR-010

Launch with `podman exec` from a lean Python launcher. The launcher reads the state file and runs `podman exec <name> -- <cmd>`.

Reason (one line): it meets NFR-004 in both runs (p95 136 and 212 ms) and keeps the container's seccomp, bounding set and groups, which the C helper drops.

Follow-ups:

- Keep the launch path's imports to what it needs. Do not import the full `ginn` CLI on the launch path. The full import adds about 70 ms.
- Do not call `podman inspect` on every launch. It costs 27 to 40 ms. Put the PID in the state file, and check the start time before use.
- Do not build `ginn-run` for v1. The roadmap (docs/roadmap.md, architecture notes, line 42) builds it only if `podman exec` misses 300 ms, and that condition was not met. If the lean launcher later misses the budget on target hardware, revisit the helper only after it matches the parity table in section 6. This spike does not edit the roadmap; the change is for the ADR author.

## 8. Risks

1. Single host, noisy. Exec p95 moved from 212 to 136 ms between runs, so the margin to 300 ms ranges from 88 to 164 ms. Re-measure on target hardware and on the musl host (S-03).
2. Launcher import growth. The real CLI import alone is about 70 ms at p95. With exec the sum reaches 285 ms in the noisy run. Keep the launch path lean and re-measure when `ginn exec` exists.
3. Helper parity gaps (section 6). Seccomp, bounding set, groups and cgroup placement are not matched.
4. Cold start is measured at 20 cycles, not the 50 per distribution that NFR-005 requires. p95 was 97 to 122 ms, far inside 2 s. The NFR-005 proof is not complete.
5. `--network host` skips network setup. Kali realms with pasta (FR-026/027) will start slower. This is not measured.
6. catatonit is missing. Without an init, PID 1 ignores signals it has no handler for, so `sleep infinity` does not stop on SIGTERM (kernel rule, not observed here). The cold path therefore used `podman stop -t 0`. FR-082 needs catatonit provided by packaging or Host Setup. It was not installed, per the spike rules.
7. The state-file PID can go stale or be reused after a restart. The start-time check guards this. Only the happy path was tested. The stale path was not.
8. The spec's nsenter flags omit `-C`, so the `nsenter` reference is not full parity. The helper does join the cgroup namespace.
