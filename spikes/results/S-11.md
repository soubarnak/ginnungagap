# S-11: derived init image and services-on boot (ADR-015 gate 0)

Date: 2026-10-15. Host: Void Linux, kernel 7.2.10_1, podman 5.8.8 with crun, rootless, user soubarna (uid 1000).
Spike: `spikes/s11/s11.py` (driver) and `spikes/s11/s11_runner.py` (runit job runner, copied from F6/F1).
Raw results: `spikes/s11/out/<distro>/summary.json` (phases, argv, sizes, boot records), `sampler.json`,
`syntax.json`, `syntax-2.json`, `rmi-by-id.json`, `keepid-storage*.json`, `probe.json`. Step logs were
kept in the session scratchpad and removed by cleanup.

## Verdict

PASS on the criterion of ADR-015 S-11: on all four distributions, `systemctl is-system-running` printed
`running` and `systemctl --failed` listed no units, in each of three boots (12 of 12). Services-off
containers from the derived images start, exec, have no systemd process (FR-082), and keep a package
installed across a restart. Several ADR-015 points need correcting (see "Corrections to ADR-015").

## Method

- Pinned digests from `src/ginn/trust/data/trust.toml`, pulled by digest on linux/amd64. The digest of each
  pulled image matched its pin.
- Provisioning container: `--user 0:0 --userns keep-id --init --entrypoint ["sleep"] infinity`, no
  `--passwd-entry`, host network, label `io.ginn.provision` only. Steps are the distribution's refresh,
  the init set (ADR-015 Decision 3), the Integration Package Set and its localedef step (host LANG
  en_US.UTF-8, from `loader.integration_set`), `/sbin/init` check, and the clean steps.
- Derived image: stage commit with USER, ENV and labels, then `create --entrypoint []` with no command
  from the stage image, then commit (see Commit syntax).
- Services-on boot: the ADR-003 argv as `src/ginn/runtime/spec.py` builds it (systemd=always, private
  cgroupns, cgroup parent `/ginn/1000/<name>`, user 0:0 with keep-id, passwd entry, host network,
  SIGRTMIN+3, `SYSTEMD_LOG_LEVEL=warning`, `--tmpfs /run/user/1000`), the eleven ADR-007 masks
  (`SERVICES_MASKED_UNITS`), the journald drop-in, `--entrypoint ["/sbin/init"]` and no command. A
  random 32-hex machine-id is `podman cp`-ed in before the first start.
- Boot, status and exec: create, cp and start run as runit jobs in the supervisor leaf (F2), through the
  user's sv directory, as the F6/F1 spike did. The session cannot exec into a services-on cgroup
  (EACCES, F2), so every exec into a services-on container also went through the leaf. Entries were
  removed after each run.
- Memory: 60 s idle after settle, then the T7.7 gate's pid set (cgroup tree, conmon, pause, runsv and
  ginn-wait), VmRSS as the budget figure and PSS beside it. Three boots per distribution.

## Verdicts

### Commit syntax (ADR-015 Decision 2f, open question 4)

Tested on debian with throwaway commits from the pinned base (`syntax.json`, `syntax-2.json`):

- `commit --change 'ENTRYPOINT []' --change 'CMD []'`: rc 0, but the image keeps the create-time
  Entrypoint `["sleep"]` and Cmd `["infinity"]`. `--change ENTRYPOINT []` alone does the same. The empty
  array is accepted and does nothing.
- `--change 'ENTRYPOINT ""'` and `--change 'CMD ""'` give `["/bin/sh","-c","\"\""]`. `null` gives
  `["/bin/sh","-c","null"]`. Both are wrong.
- `--change 'ENV K=V'` and `--change 'LABEL k='` (empty value) are accepted and applied.
- The reset works at create time. `create --entrypoint '[]'` with no command, from an image whose Cmd is
  set, gives Entrypoint null and Cmd null, and a commit of that container keeps both null. `--entrypoint ""`
  gives `[""]`, which is wrong. `--entrypoint '[]'` with a command gives that command as Cmd.

Verdict: the ADR's `--change` reset does not work on podman 5.8.8. The verified form is two commits. Commit
the provisioning container to a stage image with USER, ENV and labels. Then `create --entrypoint '[]'
<stage>` with no command, and commit that container with no change. Used in all four runs: derived
Entrypoint null, Cmd null, User 0 (debian, fedora, kali, arch).

### Environment added by podman (open question 3)

Podman added `container=podman` to the derived image on debian, kali and arch. On fedora nothing was
added, because the fedora base already sets `container=oci`. No other variable was added on any distribution.

### Keep-id storage verdict (ADR-015 Decision 11, Decision 2b)

Tested on debian (`keepid-storage-unshare.json`): create, start and a 60 MB write, with the writable
layer read inside `podman unshare`:

| | after create | after start | after 60 MB write |
|---|---|---|---|
| keep-id, upper layer bytes | 0 | 1,350 | 62,915,910 |
| no keep-id, upper layer bytes | 0 | 12 | 62,914,572 |

Verdict: keep-id does not make a second chowned copy of the base layer at create or start, and the
writable layer is the same size with and without it. Decision 11 needs no keep-id term on debian.

Caveat: the host `du` (used by the sampler, with `-x` or without) cannot read the keep-id container's
upper layer (it returned -1). With keep-id the host root size stayed at 79,414,612 bytes after the write,
against 142,328,191 without. So the keep-id peaks in the provisioning table are lower bounds. The no-keep
debian run in the corrected re-run (`--nokeep`) shows the same provisioning writes on the host at commit:
root 194,778,719 bytes, against 117,927,472 for the keep-id commit.

### rmi verdict (ADR-015 Decision 13)

Podman 5.8.8 does not refuse `rmi` of the base while a derived child exists. The call returns rc 0 and
untags the pinned reference, and the base image is gone afterwards. The child images stay, and they run
and remove normally. So the ADR's claim that podman refuses this removal is wrong. The removal order of
Decision 13 (derived images first, then the base) is still the right order, but it cannot be relied on as
a check. The removal must select each image by ID and must not depend on a refusal.

## Corrections to ADR-015

1. Decision 2f and open question 4: replace the `--change 'ENTRYPOINT []'` and `--change 'CMD []'` commit
   with the two-commit reset (stage commit, then `create --entrypoint []` with no command, then commit).
   The change-only form keeps the create-time entrypoint and command.
2. Decision 4: once the reset is in, the services-on container has no command, so `/sbin/init` gets no
   argument from the image. The four boots record Entrypoint `/sbin/init` and Cmd null. The sentence "the
   image's command cannot reach `/sbin/init`" holds only with the reset. It was not checked on a
   chain-committed image.
3. Decision 13 (and Decision 13's "podman refuses to remove the base" sentence): remove the refusal claim.
   Keep the derived-first order and select each image by ID.
4. Decision 3, arch clean: `pacman --sync --clean --clean --noconfirm` does not clear the package cache.
   With `--noconfirm`, pacman answers the "remove ALL files from cache?" prompt with its default N, so 4
   cached packages (2,606,348 bytes) remain. A later install still works (the services-off htop install
   after the clean, rc 0), so ADR-011's rule holds for the sync databases (open question 5). The cache
   needs another argv. Not tested here: remove `/var/cache/pacman/pkg` with `rm -rf` and recreate it
   with `mkdir -p`.
5. Decision 11 storage: the keep-id term is zero on debian (see Keep-id storage verdict). The tmpdir
   commit check (`estimate_required(init_delta + ips_delta)`) is far above the measured use (under 1 MB at
   commit on all four). The host `du` must not be used to measure keep-id layers (see Caveat above).
6. Decision 2c and open question 2: the names `systemd dbus-broker` (fedora) and `systemd systemd-sysv dbus`
   (debian, kali) install and boot. Their sizes are in the table above, ready for the T7.17 data.

## Findings and open items

- The arch boot run 3 read VmRSS 12.21 MiB and PSS 7.45 MiB, against 33.98 and 34.27 MiB in runs 1 and 2.
  The sample counted the same four processes (systemd, journald, dbus-broker-launch, dbus-broker) and the
  same helpers. Host MemAvailable at that run was higher (8.86 GB, against 8.14 and 6.56 GB), so memory
  reclaim does not explain it. The cause is not identified. The median (33.98 MiB) is the figure to use.
  Re-measure arch before NFR-003 is judged.
- Fedora is over the NFR-003 budget on VmRSS at 62.25 MiB, while its PSS (22.95 MiB) is in line with the
  other distributions. The fedora extra processes were not profiled.
- Rootless podman reports `Supports shifting: false` for the overlay store (`probe.json`). The keep-id test
  above found no copy regardless.
- The podman store reports `imageCopyTmpDir: /var/tmp`. Pulls here did not write there, but this is outside
  the Owned Paths and should be checked in the host gate.
- Debian run 1 (before the reset fix) passed the same boot criterion (`summary-run1-pre-fix.json`, 3 of 3).
  Its derived image kept Cmd `["infinity"]`, and it is superseded by the corrected debian re-run above.
- NFR-021 (five realms) and NFR-008 (steady state against base plus 200 MiB) were not measured. The derived
  deltas in the table (33 to 53 MB) are the input to NFR-008.

## Cleanup

`s11.py cleanup` removed every spike container (none were left), every spike image (base and derived, by
ID), the storage and tmpdir (`podman unshare rm`), the spike runtime dir `/run/user/1000/s11`, the runit
job entries under the user's sv directory (empty afterwards), the `/ginn/1000/s11*` cgroup leaves, and the
spike's pause process. Monitor `tail` processes were stopped, and the scratchpad `s11` directory was
removed. The user's `~/.local/share/containers` mtime was unchanged across the run (1791786933.346658657
before and after). `/run/user/1000/libpod` was never read or written.
