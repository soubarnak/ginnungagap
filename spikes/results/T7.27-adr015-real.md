## Product failures

Evidence is the gate log. Each entry names the code site that raises or decides the behaviour.

**F1. Services-on rebuild refused with GINN-E-REALM-USER on all four distributions (items 7a and 7b).**
The error detail is `found 'soubarna:*:1000:1000:Soubarna:/:/bin/sh', expected
'soubarna:*:1000:1000:soubarna:/home/soubarna:/bin/bash'`. The host entry (`getent passwd soubarna`)
is the expected one. The check runs in the rebuild at `src/ginn/ops/rebuild.py:398` (`_check_user`).
It raises at `src/ginn/ops/create.py:696`, when `getent passwd <uid>` in the new container does not
equal `spec.passwd_entry` (`create.py:675-698`, `realm_passwd_entry` in `src/ginn/runtime/spec.py:254`).
The same check at create (`create.py:341`) passes in the fixture, so the difference is in the rebuilt
container. Its passwd entry is not the one ginn sent with `--passwd-entry`. The likely source is the
image the rebuild starts from (the derived or pinned image's `/etc/passwd`), but this is not isolated.
It needs a probe that reads the rebuilt container's `/etc/passwd` and the image's `/etc/passwd`.
The old root is kept after the failure (NFR-031), so the realms stayed usable.

**F2. A services-on start does not rebuild (item 3, debian, fedora and arch).**
After `ginn stop`, `ginn services <name> on` and `ginn start`, the realm stayed at generation 1 with PID 1
`podman-init` (its services-off root). The start returned rc 0. The lazy rebuild of a services change
fails and falls back to the old root with GINN-W-REBUILD-DEFERRED (`src/ginn/ops/lifecycle.py:545-578`).
That fallback is the probable cause of this symptom, and F1 is the probable cause of the failed rebuild.
Not confirmed: the gate did not capture the start's warnings, since it asserts only rc 0. To confirm,
the test should record the `ginn start` warning codes in its log line.

**F3. Kali package change refused: GINN-E-NOT-SUPPORTED-YET (items 1 and 3, kali).**
`ginn install` on a Kali realm returns `realm 't727-kali-svc' cannot be used yet: a package change in a
Kali realm arrives in M10`. The refusal is at `src/ginn/ops/packages.py:150-151`. This blocks the cron
install (item 1) and the htop install (item 3). It is a milestone gate, not a crash, and it may be the
intended state until M10. The owner decides whether T7.27 items 1 and 3 wait for M10 for kali.

**F4. Kali exec refused: GINN-E-NOT-SUPPORTED-YET (item 6, kali).**
`ginn exec --root` into a Kali realm returns rc 125 with `a Kali realm arrives in M10`, from
`src/ginn/runtime/enter.py:247-248`. The exec in item 6 is the first call into the realm, so the mask
read did not run. Item 2 (kali) passed because it does not use exec. Same owner decision as F3.

Items 7a and 7b on kali fail with F1, not with F3 or F4. The rebuild path does not depend on Kali's

### Product failure (new): F5, the replay of apt packages reports them missing

The replay of an apt-based realm (debian, kali) returns GINN-W-REPLAY-MISSING for packages that exist
upstream. For item 7a the warning names `cron`: its message is `package cron is no longer available
upstream` (seen twice in the log: debian and kali). For item 3 the warning names a package that the
gate did not print, and htop is absent from gen 2 on both distributions, so it is probably htop
(not confirmed). Fedora and arch replay with no warning.

Evidence and code sites (not confirmed by a probe):

- The replay installs with the install verb only. `src/ginn/ops/rebuild.py:727-744` (`_install_repo`)
  calls `definition.argv(Verb.INSTALL, batch)` and no refresh step.
- The refresh runs only in the install path: `src/ginn/ops/packages.py:375-387` (`Verb.INSTALL in
  definition.refresh_before`). The rebuild path (`rebuild.py`) has no such check.
- Debian and Kali list `install` in `refresh_before` (`src/ginn/distros/data/debian.toml:31`, and the
  same line in kali.toml), so a plain install refreshes first and a replay does not.
- The provisioning clean steps empty the apt lists: `src/ginn/distros/data/debian.toml:100-106`
  (`apt-get clean`, `rm -rf /var/lib/apt/lists`). A derived image therefore has no lists, and apt on
  its replay reports `Unable to locate package`.
- That text matches `missing_package_regex` (`debian.toml:28`). `src/ginn/ops/rebuild.py:266-280`
  (`_is_missing`) takes it as positive evidence that the package is gone upstream, and
  `rebuild.py:1146` raises GINN-W-REPLAY-MISSING.

Likely fix (for the owner to decide): the replay refreshes the package lists before its first install,
as `install_packages` does, or the clean steps keep the lists. The apt output is not captured by the
gate. Confirming `Unable to locate package` needs the apt output of the replay call, which the gate
does not record. A probe can read it from the replay's exec output, or the gate can record the
package list and message of each REPLAY-MISSING warning.

### Method

- NFR-003: one services-on realm per distribution. Ten runs: start, idle for 60 s (the settle time,
  recorded per run as 60.25 to 60.94 s), sample `realm_rss` and `host_memory`, stop. The verdict is the
  median of the ten VmRSS values (`statistics.median`). PSS is recorded beside it.
- NFR-021: five services-on realms per distribution, started together. The settle time is 60 s after the
  last start. Three samples follow at 60, 90 and 120 s after the last start. Each realm's median VmRSS is
  compared with the 40 MiB budget. Every realm must read `running` in every sample. The relay listener is
  recorded beside the five (ADR-014) and included in the total.
- NFR-008: one services-on realm per distribution, with no `--with`. The disk use is taken after create
  (stopped), and again at steady state after 60 s running. The total is the derived image's size (as
  podman reports it), plus the container's writable layer (`container inspect --size`), plus the Realm Home
  (`ginn status`, FR-020). The official image size is the size of the pinned base, found by the derived
  image's `io.ginn.base-digest` label (ADR-015 Decision 10). The target is that size plus 200 MiB. A
  second column adds the base once more, as an upper bound.
