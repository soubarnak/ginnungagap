## 3. Harness, and where it departs from the brief

- **Real supervisor, not conftest's temp base.** The gate drives `ginn --json ...` against `~/.local/state/ginn/sv`.
- **Launcher, no root.** `/usr/libexec/ginn` does not exist here. The gate writes a launcher under `/tmp` that sets `_context.WAIT_HELPER` and `attach.DEFAULT_HELPER` to `native/build`, then calls the product's `main()`. The packaging path (`make install` into `/usr/libexec/ginn`) is not proven.
- **`leaf_exec`.** In-realm commands run as a throwaway runit service (`t77-exec-*`). The sweep now also retires every `t77-exec-*` directory left in the sv directory (with `_retire`), and removes their `.tmp` directories.
- **No run-time XFAIL.** `need_running` and `pytest.xfail` are removed. A failed start is an assertion (`start_ok`). A known product gap is a declarative `@pytest.mark.xfail(strict=True, reason="F<n>: ...")` on the item, so an unexpected pass fails the suite.
- **Strict marks and KnownGap.** Every known-gap item carries `xfail(strict=True, raises=KnownGap)`. `KnownGap(AssertionError)` is raised only where the gap shows: `start_ok` for F1, the FR-083 REBUILD-DEFERRED check (F2/F7), the AC-3 `state == "failed"` check (F10), and the NFR-003 and NFR-021 budget checks (F11). A failure of any other kind stays a failure, and so does an unexpected pass (strict). F1 is matched on two facts, not on text: the start error code is GINN-E-INTERNAL or GINN-E-SERVICE-TIMEOUT, and the realm's image has no `/sbin/init` (`podman cp` of that path from the created container fails). The error body does not carry `/sbin/init` (F3), and this round's debian and fedora starts gave GINN-E-INTERNAL, so a text match on SERVICE-TIMEOUT or `/sbin/init` would not have matched them.
- **FR-081 AC-2 check.** The restart is measured in the 10 s window: a new run pid, then `wait_run_with_init(not_pid=old_init)`, then `ginn status` read until it reads `running`. The first version read the state once, when the new init appeared. The record reads `failed` from the crash until the restart's start completes (lifecycle.py crash path, F13), so that read failed in the first pass (run 6.92 s). The AC-2 item now polls the state inside the window, and the re-run passed (7.64 s).
- **FR-081 AC-3 kill pattern (unchanged, the F10 trigger).** Each kill targets the first new container init that `wait_run_with_init` sees. That is during the restart's attach (section 7), not after the realm has settled.
- **Kill guard.** AC-2 and AC-3 kill only a positive, fresh container init (`wait_run_with_init`). Pid 0 is never signalled.
- **RSS attribution (ADR-007 method).** Per sample: the realm's cgroup tree, conmon, runsv, ginn-wait, and ginn's store pause (counted once). The budget is the VmRSS sum (the spec's RSS). `Pss` from `/proc/<pid>/smaps_rollup` is recorded beside it, and each process whose Pss cannot be read is counted in `pss_unreadable`. In this run every process was readable (0 unreadable).
- **uid.** `UID = os.getuid()`. The cgroup root is `/sys/fs/cgroup/ginn/<uid>`, the runtime root is `paths.runtime`, and no `1000` is hard-coded.
- **Sample count.** `GINN_T77_SAMPLES`, default 10 (the roadmap count). NFR-021 used five realms and one 60 s settle.
- **Realms.** Every realm is named `t77-...`. The module sweeps stale ones at the start and removes its own at the end, along with its empty cgroup directories (F9).
- **test_nfr002.** The runsv is retired with `sv down` and `sv exit` (`_retire`), and every process is killed and waited on before the test returns.
- **Podman calls.** Through the product adapter's global flags, with ginn's own storage and `paths.runtime`. Nothing touches `~/.local/share/containers` or `/run/user/<uid>/libpod`.
- **Trace harness (F10, not product).** The F10 traces used a launcher and drivers in the session scratchpad (`f10/bin/ginn`, `f10/drive*.py`), not in the repo. The launcher runs each supervised `_service-run` under `strace -f -ff`. Under that wrapper, runit's `run` process is `strace`, so `sv down` (TERM) does not reach the traced chain. `ginn stop` then timed out (GINN-E-SERVICE-TIMEOUT), and the realm had to be removed by hand. That is an artifact of the trace harness, not product evidence.

## 7. Findings

- **F1 (product gap: services-on does not boot on debian or fedora).** Their pinned images have no `/sbin/init`, and the services-on integration step that would install systemd at start is not built (T7.3 and T7.4 leave it pending). The runit start fails with `crun: executable file /sbin/init not found` (captured from inside the supervisor leaf). The create warning says the integration set comes with `ginn rebuild`, but the rebuild starts the new generation with `/sbin/init` before it replays, so that path fails too. Arch's base image ships systemd, and arch boots.
- **F2 (product gap: a user session cannot exec, enter, install or attach into a services-on realm).** `ginn exec --root` and raw `podman exec` from a session process both fail: `crun: write to /sys/fs/cgroup/ginn/1000/<realm>/libpod-*/cgroup.procs: Permission denied`. The cause is that moving a process into the realm cgroup needs write access to the common ancestor's `cgroup.procs`, which is root-owned. Only processes inside the supervisor leaf reach the realm. `ginn install` on a services-on realm is exec-based, so it fails the same way. A product route for user exec into services-on realms is a design item (ADR-003). It is not built here. The F10 trace (below) does not change F2: the supervised path does not use that route.
- **F3 (error reporting).** A missing init surfaces as GINN-E-INTERNAL with "this is a bug" (exit 70, from crun's exit 125), and as GINN-E-SERVICE-TIMEOUT "runsv stopped the service after repeated crashes" in the start. The crun message is in neither, and `ginn log` shows only the code. In the F10 traces an INTERNAL start exited 70 after its `podman stop`, and the message hid the step (`service-run.stderr` holds only the code). A specific code is needed (errors catalogue).
- **F4 (works as designed).** A failed lazy rebuild leaves the realm running on its services-off generation with GINN-W-REBUILD-DEFERRED, and removes the failed generation's container (FR-083 debian run 1, earlier).
- **F5 (environment).** `/usr/libexec/ginn` is absent, so `ginn-idle` is not armed here and services-off starts print GINN-W-IDLE-STOP. The warning says so.
- **F6 (arch degraded; tracked open item).** `degraded` with 7 failed units: `dbus-broker.service`, `systemd-firstboot.service`, `systemd-homed.service`, `systemd-resolved.service`, `dbus.socket`, `systemd-resolved-monitor.socket`, `systemd-resolved-varlink.socket`. The S-01 criterion asks for zero failed default units, so arch does not meet it. FR-080 AC-1 and AC-2 need only the enabled unit to be active, and that holds. The arch realm's extra processes (about 13 against 4 for S-05's debian image, section 5) come from the same units. The fix is to mask or configure them (systemd units to fix or mask). Tracked open item (section 10).
- **F7 (services change is not applied from a user session).** Same mechanism as F2: the rebuild's grant attach and replay run as `podman exec` from the CLI process (`src/ginn/ops/rebuild.py`, `_attach` after `_start_through_sv`). The rebuild starts gN+1 under runit, which works on arch, and then fails. Fixing it needs the exec route of F2 first.
- **F8 (instance of F2 in the rebuild).** The audit log for the FR-083 arch realm: `rebuild error GINN-E-ATTACH-FAILED` for generation 1 to 2.
- **F9 (cgroup leftovers).** `ginn delete` leaves an empty `/sys/fs/cgroup/ginn/1000/<realm>` directory behind, and so does podman. Verified: directories from earlier deleted realms were still present, empty and user-owned. The gate's sweep removes its own empty `t77*` directories, and the F10 traces needed one manual `rmdir` each. Product fix (who removes the realm cgroup) is a design item.
- **F10 (FR-081 AC-3 gives `stopped`, not `failed`: a kill during a supervised start's attach).** Details below.
- **F11 (budget).** Under the spec's VmRSS method, arch's services-on realm misses NFR-003 at 87 MiB (median), and five of them miss NFR-021 at 437 MiB. PSS is about 24.5 MiB per realm (gate attribution). The budget method is open: a VmRSS budget counts the shared libraries once per process, while PSS does not. This is the ADR-007 budget question, and the orchestrator decides it, or further mitigation of arch's helper processes (userdbd, userwork, nsresourced; F6).
- **F12 (tested and found working, undisturbed starts).** The lazy attach of the FR-049 enter path and the runsv start path both work for arch when the container is not disturbed: FR-084 start (2.74 s), FR-081 restart (AC-2, 7.64 s), and six traced restarts in F10 run T1. Only session-scope exec and attach fail (F2). F10 shows the one disturbed case that fails (below).
- **F13 (the record reads `failed` from the start of a restart until its start completes, by design).** A crash of a running realm moves its record to `failed` (lifecycle.py:1035, "a crash: running to failed (DR-020)"). The restart's successful start moves it back to `running` (domain/states.py allows FAILED to RUNNING). So `ginn status` reads `failed` from the start of the restart until its start completes. In the F10 AC-2 trace (3 cycles), `ginn status` read `failed` when the new init appeared in each cycle, and read `running` 20 s later, with one `start ok` in the audit per cycle. This is product behaviour, not a gap. The gate polls the state inside its window (section 3).

### F10 trace (2026-10-14): does the attach fail from the supervisor leaf?

**Question.** Does the supervised restart's attach fail even from inside `/ginn/<uid>/supervisor` (wider than the session-only F2), or does it succeed there and fail for another reason?

**Method.** The launcher ran every supervised `_service-run` (the realm's runit `run`) under `strace -f -ff -y -tt -s 400` and kept one run directory per invocation. The traced calls were `openat`, `write`, `execve`, `clone`, `clone3`, `exit_group`, `mkdir`, `mkdirat` and `rmdir`. Each run directory holds the run's `/proc/self/cgroup`, its stderr, and one trace file per process. A harness driver killed the container init (`SIGKILL`) and read the audit log and the realm cgroup subtree (`cgroup.procs` with owner, `cgroup.subtree_control`, `cgroup.type`, `cgroup.events`) every 0.25 s. The driver and a `bash -lc` login shell were compared with the restart's cgroup. Excerpts (the timeline, the clone3 lines and the errno summary) are in `spikes/results/T7.7-f10-trace.txt`. The raw per-process traces are kept only in the session scratchpad, not in the repository.

**Runs.**

- T1 (six restarts, each kill 8 s after the previous restart): 6 of 6 starts `ok`, restarts 9.1 to 10.7 s (driver-measured under strace).
- T2 (the gate's AC-3 kill pattern, under trace): audit `start GINN-E-INTERNAL`, `start GINN-E-ATTACH-FAILED` three times, then `service-exit gave-up, state_kept: stopped`.
- T3 (the same five kills, each 3 s after the new init appeared): four starts `ok`, then `service-exit gave-up` with no `state_kept`, which means the realm moved to `failed`.
- T4 (kills after `ginn status` read `running`): the same ATTACH and INTERNAL failures as T2. The record reads `running` from before the restart until the failed start stops it, so that wait does not detect a start in progress.
- T5 (the AC-2 sequence, three fresh realms, traced): each restart `start ok` at 10.8 to 11.1 s; `ginn status` read `failed` at the restart and `running` after 20 s (F13).

**Answers, with the evidence.**

1. **Where the supervised start runs.** Every traced `_service-run` read `0::/ginn/1000/supervisor` from `/proc/self/cgroup` at its start (`wrapper-cgroup`, all runs). Its children, the `podman start`, `podman exec` and `crun` processes, descend from it. The supervisor leaf is where runsv sits (section 7, F2 and the supervisor leaf).
2. **Does the attach's cgroup write fail?** No write to any `cgroup.procs` occurs in any traced restart. The exec moves the process into the container cgroup at creation: `clone3({flags=CLONE_INTO_CGROUP, ..., cgroup=N}, 88)` returns a pid. Every into-cgroup clone in the traces succeeded: T1 177 clones and 0 failed, and the five T2 restart directories 7 clones and 0 failed. No EACCES and no EPERM appears on any realm cgroup path. The realm-cgroup errnos are EEXIST on `mkdir` of the realm directory, ENOENT on the `cgroup.subtree_control` write during creation, and EBUSY on `rmdir` of an old `libpod-*` cgroup. The other EACCES results are config and probe reads, writes to the root cgroups' `cgroup.subtree_control`, and `oom_score_adj` writes. They occur in successful and failed starts alike, and none is on the attach path (`spikes/results/T7.7-f10-trace.txt`).
3. **Why the failing starts fail.** The failing exec is refused by podman, before any kernel call, with `GINN-E-ATTACH-FAILED: attaching the grants into the realm failed: Error: can only create exec sessions on running containers: container state improper`. The container had already exited. Run 1791992780521851521-427 (T2), local time: `podman start` 21:16:23.410, `podman inspect` 21:16:23.608 (the new init is visible), the driver's `SIGKILL` to init pid 1175 at 21:16:23.654 (the process reports `+++ killed by SIGKILL +++` at 23.655), and the attach's `podman exec` at 21:16:23.807. The kill came 0.15 s before the exec.
4. **Why T2 kills during the attach.** The AC-3 loop waits only for a new init pid (`wait_run_with_init`) before each kill. That pid is visible as soon as `podman start` returns, while `_service-run` is still attaching. Each ATTACH-FAILED in T2 is preceded by such a kill, and T3 (a 3 s settle before each kill) shows four `ok` starts. So the AC-3 failures come from the test's kill timing, and the product cannot be blamed for a kill it could not have survived. The product gap is that a crash during the start stops the realm (see 6).
5. **Old container cgroup.** The trace shows `rmdir` of the previous `libpod-<old id>` cgroup returning EBUSY while the restart runs (T2, T5). That is podman's cleanup of the old container, and it is not on the attach path (the failing check is podman's container-state test). It is not established as a cause.
6. **What the product does.** A failed start after a container death stops the realm (`lifecycle.py` "leaves the realm stopped, and fails the start with GINN-E-ATTACH-FAILED"). A crash of a running realm moves it to `failed` (lifecycle.py, DR-020). A crash-limit give-up on a stopped realm keeps it `stopped`: `_record_failed` (src/ginn/ops/service.py:414-438) records "a stopped realm stays stopped, because DR-020 has no stopped-to-failed move", and the transition table in src/ginn/domain/states.py:39 has no stopped-to-failed edge. The record never reaches running in the disturbed start, so the give-up has no running realm to move. So five crashes that all land during a start end `stopped`, and FR-081 AC-3 needs `failed`. T3 shows the give-up does reach `failed` when the realm is running between crashes.

**Conclusion.** The attach does not fail from the supervisor leaf for any ownership or cgroup reason. Its `podman exec` is refused only when the container has already died, and the traces show the kill landing in that window. F2 stays a session-only gap, and it is not widened by this trace. F10 as the AC-3 gap is a product-semantics question (should crashes during a start count towards a `failed` give-up?) with a test-timing trigger (the gate kills before the start has attached). This is a design item for an ADR. The gate's AC-3 is kept as written, and its strict xfail reason names the mechanism.

**F12 reconciled with F10.** F12 holds for undisturbed starts: all six restarts in T1 and the AC-2 restarts (T5 and the gate) succeeded. F10 is the one disturbed case, a container that dies during its own start. The two statements are both true now.

**User decision, 2026-10-14.** A crash during a start counts toward the FR-081 give-up, so the realm ends `failed` (a DR-020 amendment). This is implemented on the F2 branch, not in the review round. The AC-3 item keeps its strict xfail (F10) until that branch lands.

Not captured: the step inside `_service-run` that raised GINN-E-INTERNAL (T2, run 30600). The product hides it (F3). In that run the container was killed 0.4 s after `podman start`, and the process exited with code 70 after `podman stop`. The kill-during-start pattern is the same, but the step is not recorded.
