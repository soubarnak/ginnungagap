## Findings

1. Nested `newuidmap` needs CAP_SYS_ADMIN in the outer container's user namespace. A1 and A3 fail with `write to uid_map failed: Operation not permitted`. A4 gets past `newuidmap` and fails only at tun, and A5 passes. The mechanism is consistent with the kernel's `uid_map` write check requiring CAP_SYS_ADMIN over the target namespace. I did not re-check that against kernel source in this spike.
2. The realm user holds SYS_ADMIN, not only the setuid helper. Podman sets ambient caps for non-root `--cap-add`, so `CapEff` and `CapAmb` of the realm user are `0x200000` (dump in `caps.txt`). Narrowing the grant to file caps on `newuidmap` alone was not tested. Podman's ambient handling likely prevents it.
3. Single mapping (no subuid) cannot run alpine: `lchown /etc/shadow: invalid argument` (requested gid 42). A7. So AC-3 needs subordinate IDs, and therefore needs NFR-SEC-002 to allow SYS_ADMIN.
4. The realm image's `useradd` writes `dev:100000:65536` into `/etc/subuid`, which is not mapped in the nested namespace. Any realm image that uses nested rootless podman must overwrite it with a valid range at creation time.
5. Two inner subuid lines work (A6), with inner 0..65535 in one map. This includes inner uid 65534 (`nobody`). A single range from 1001 holds at most 64536 IDs, so `nobody` cannot be mapped with a single range (arithmetic below). I had assumed contiguity was a hard limit. The multi-line result shows it is not.
6. `--network host` for the inner container works with no tun (N5). The inner default network (pasta) and slirp4netns work with tun present (N1, N4). `--network none` works (N3).
7. Default seccomp is sufficient with SYS_ADMIN (A5 and all N and M rows pass with it).
8. An unexplained `podman exec` failure (`nsexec: failed to open /proc/<pid>/ns/user: Permission denied`) hit one exploration container during a manual test sequence. It did not recur in the matrix (no `nsexec` errors in any log), and I did not explain it.
9. `/dev/kvm` in the realm shows as `nobody:nogroup`. The realm user and container root both get EACCES (FR-062 AC-4). `--group-add keep-groups` (on runc, with no crun) leaves the realm user with only `dev`; the host gid 24 is unmapped, so it is dropped. A candidate fix is a Host Setup ACL (`setfacl -m u:<user>:rw /dev/kvm`), which maps through keep-id uid 1000. That is a root step and was not tested.

## Arithmetic (AS-005)

- The outer map has 65537 container IDs (0..65536). Container 0 is the outer root (not exposed to the inner map). Container 1000 is the realm user.
- A full inner range of 65536 IDs (inner 0..65535) needs container IDs 1..65536 except 1000 (inner 0 maps to 1000), i.e. 65536 IDs drawn from `{1..C}` where C is the outer subordinate count. Excluding container 0 requires C >= 65536. Using container 0 would reduce this to C >= 65535.
- So one nested level needs at least 65536 host subordinate IDs for the user, with zero slack. This host has exactly that.
- A single contiguous range cannot give the full 65536. From 1001 the maximum is 64536 (container 1001..65536), so it cannot map inner 65534.
- The brief predicted `>= 65536 + 1 + inner 65536`. That double-counts: the realm's own container ID 1000 is reused for inner root, and container 0 is excluded, so the requirement is 65536 in total, not 131073.
- The SRS value 524,288 is 8x the floor. Every rootless container shares the same map, so this design does not consume it per realm; `--userns auto` style allocation would. It is sufficient.
- Host Setup must write `<user>:<start>:524288` into both `/etc/subuid` and `/etc/subgid`, non-overlapping with existing entries and without changing the existing `soubarna:100000:65536` line. Existing entries on this host: `root:1000:1`, `root:59990:1`, `soubarna:100000:65536`, `act-runner:200000:65536`, `root:1000000:65536`. The block `265536..789823` is free today; Host Setup must compute the start at run time. Untested: whether podman uses both outer ranges (the inner multi-range result suggests it does, same code path). Podman's stored layers also need `podman system migrate` after a subuid change (expected, not tested).

## S-07d: newuidmap EPERM root cause

Run: 2026-10-12, same host as S-07c (Void glibc x86_64, kernel 7.2.9_1, rootless podman 5.8.8, crun 1.30.1). Script: `spikes/s07d_newuidmap.sh` (stages `evidence`, `fix setcap`, `diag`, `diag2`, `seccomp`, `final`, `teardown`). Image: `spikes/Dockerfile.s07d`, which is the S-07 image plus `libcap2-bin` and a `FIX` build argument. Raw logs, `attempts.tsv` and the generated seccomp profile are in `~/.cache/ginn-spike/s07d`, outside the repo. Every podman call passes `--root`, `--runroot` and `--tmpdir` at the spike directories. Every outer run passes `--runtime crun`. No `--privileged`, no sudo, no xbps. The inner podman uses the S-07c C2 configuration: uid 1000, cgroupfs, file events, fuse-overlayfs, subuid `dev:1001:64000`. The base `debian:stable` is unpinned, as in S-07 and S-07c.

### Hypotheses

H1, setuid bit or file capability lost during image unpack: refuted for the setuid bit. In the outer container, `ls -ln` and `stat` show mode 4755 (`-rwsr-xr-x`), owner 0:0, on `/usr/bin/newuidmap` and `/usr/bin/newgidmap` (P1, P2). The image layer, read with `podman image mount` inside `podman unshare` (`layer-none.txt`), shows the same. `getcap` prints nothing for the unfixed image, which is expected: that image never carried file capabilities.

H2, no_new_privs: refuted. `NoNewPrivs: 0` in P1 and P2. `Seccomp: 2` (filter mode) in both.

H3, bounding set lacks CAP_SETUID or CAP_SETGID: refuted. Without SYS_ADMIN the realm user has `CapBnd 0x800405fb`, which decodes to cap_setuid and cap_setgid among others, and empty CapPrm, CapEff and CapAmb. The bounding set is not the gap. The gap is in what the setuid exec gives the helper (T1 below).

H4, requested ranges not mapped in the outer userns: refuted. The outer `uid_map` and `gid_map` as the container sees them are `0 1 1000`, `1000 0 1` and `1001 1001 64536`. Container ids 1001 to 65536 are mapped, which covers the requested inner range (outer ids 1001 to 65000). With the spike range `dev:1001:64000` written to `/etc/subuid`, newuidmap's policy check accepts the request and the multi-range write reaches the kernel, which then refuses it. The first pass of P1 used the image's default `/etc/subuid` (`dev:100000:65536`), and newuidmap refused at its own policy check (`uid range [1-64001) -> [1001-65001) not allowed`). That was a fault in the probe, not evidence about the spike range. The probe was corrected to write the spike subuid first, and P1 was rerun; the results reported here come from the rerun.

Root cause, not one of H1 to H4: the kernel refuses the uid_map write. Evidence:
- P1, no SYS_ADMIN: a direct `newuidmap` multi-range call and a single-range call (`0 1000 1`, which needs no subordinate range) both fail with `write to uid_map failed: Operation not permitted`. The single-range failure rules out the range policy.
- P2, same flags plus SYS_ADMIN: both calls pass.
- T1 (P1, realm user): a setuid-root copy of sleep runs with `Uid 1000 0 0 0` and `CapEff 0x800405fb`. The child has euid 0 and CAP_SETUID but not CAP_SYS_ADMIN. In P2 the same child has CAP_SYS_ADMIN in CapEff.
- F1 (setcap image, no SYS_ADMIN): multi-range and single-range both pass.

The explanation that fits all of this: the kernel's `map_write` requires CAP_SYS_ADMIN over the target user namespace, and `cap_capable` grants that without any capability to a writer whose euid is the namespace owner (here the realm user, uid 1000). A setuid-root `newuidmap` has euid 0, not the owner, so it needs CAP_SYS_ADMIN in its effective set. This comes from my reading of `kernel/user_namespace.c` and `security/commoncap.c`, not from re-reading the source during this run. The probes above are the evidence.

### Fix 1: file capabilities, no setuid bit (FIX=setcap)

`Dockerfile.s07d` with `FIX=setcap`: `chmod 0755` on both helpers, `setcap cap_setuid=ep` on newuidmap and `setcap cap_setgid=ep` on newgidmap. `layer-setcap.txt` shows both capabilities in the image layer, with mode 0755.

- F1, probe, no SYS_ADMIN: multi-range `rc=0` (`0 1000 1` and `1 1001 64000` written), single-range `rc=0`. The file-capability copy in T2 runs as `Uid 1000 1000 1000 1000` with `CapEff 0x80`. Euid stays at the owner's uid, which is the case the owner rule covers.
- F2, C2 with the chosen set, no SYS_ADMIN: outer rc 0, inner rc 126. First error: `Error: crun: sethostname: Operation not permitted: OCI permission denied`. The newuidmap blocker is gone. The inner image pull succeeds; the failure is at container start.
- G3, control, FIX=none (setuid helpers), narrow seccomp, no label, no SYS_ADMIN: inner rc 125, `newuidmap: write to uid_map failed: Operation not permitted`. So the file-capability change is needed.
- Restoring mode 4755 (the other option in the brief) was not run. H1 showed the bit already set, so that would reproduce the unfixed image.

### Finding 1: `--root` on the command line drops storage.conf options (podman 5.4.2)

Diagnostic in a container with the E1 outer flags. `podman info` graphOptions for each inner form:

- no flags: `overlay.ignore_chown_errors: "true"` and `overlay.mount_program` loaded from storage.conf.
- `--root` alone: `map[]`, options dropped.
- `--tmpdir` alone: loaded.
- `--runroot` alone and the three-flag form: printed nothing. The error text was not captured, so this is not resolved.
- `--root` plus `--storage-opt` on the CLI: image pulls, unpacks and runs (E1o).

ginn passes `--root` on every podman call (`docs/capabilities.md` base argv, ADR-004, IR-020). Whatever sets `ignore_chown_errors` for a realm's inner podman must therefore go on the command line, or the inner podman must find its root without `--root`. Checked only on podman 5.4.2.

### Finding 2: newuidmap is not invoked in single-uid mode

E1o: inner uid_map and gid_map are each one entry, `0 1000 1`. `podman info` idMappings shows one uidmap and one gidmap entry. The debug run produced 106 log lines and no line naming newuidmap or newgidmap. The control shows the grep can match: E0's error names `/usr/bin/newuidmap` as soon as the helper runs. The message `cannot find UID/GID for user dev: no subuid ranges found` is logged at level=error. It is podman's single-mapping fallback, not a failure, and E1o passes with it.

The setuid helpers stay in the realm image unchanged (`-rwsr-xr-x`, E1o-realm). They are present but unused.

### Finding 3: seccomp rule and setdomainname

`spikes/s07e_seccomp.py` reads `/usr/share/containers/seccomp.json` (40 rules). The host file names both calls in two rules, both at 0-based index: 15 (ALLOW when the process holds CAP_SYS_ADMIN; names `bpf`, `lookup_dcookie`, `quotactl`, `quotactl_fd`, `setdomainname`, `sethostname`, `setns`) and 16 (ERRNO when it does not; names `lookup_dcookie`, `perf_event_open`, `quotactl`, `quotactl_fd`, `setdomainname`, `sethostname`, `setns`).

- `seccomp-s07e-both.json` (both names): both names are removed from rules 15 and 16. The other names in those rules keep their original conditions. One rule is inserted at the front: names `["setdomainname", "sethostname"]`, action `SCMP_ACT_ALLOW`, no args, no includes, no excludes. Default action (SCMP_ACT_ERRNO) and the other rules are unchanged. The script removed 4 name entries; the file has 41 rules.
- `seccomp-s07e-host.json` (sethostname only): the same change for `sethostname` alone. It removed 2 name entries. `setdomainname` keeps its original conditions in 15 and 16.

Both files are accepted by `podman run --security-opt seccomp=<file>` (E1o and E4c start). Without SYS_ADMIN, the default profile gives EPERM for both calls (E4-none, E3). With the both-names profile both calls succeed in the probe (E4-both). With the sethostname-only profile, `setdomainname` still returns EPERM (E4-host). The kernel allows it in the same namespace setup under the both-names profile, so the EPERM comes from the filter rule that still gates it. AC-3 passes with that rule still gating `setdomainname` (E4c). So setdomainname does not need ungating for AC-3: the inner podman sets only the hostname of its private UTS namespace.

Not tested: an inner container that sets `--domainname`. Under the sethostname-only profile it would be expected to fail at setdomainname. ADR-006 and `docs/capabilities.md` currently ungate both names. This spike suggests narrowing to sethostname only; the user decides.

### Finding 4: minimal outer set

- overlay (E1o): `/dev/net/tun` is needed (E5a: pasta fails). `unmask=/proc/*` is needed (E5b: `ping_group_range` fails). `/dev/fuse` is needed by the fuse-overlayfs mount program. The seccomp profile must ungate sethostname (E3 fails with the default profile).
- vfs (E5c): passes without `/dev/fuse`. vfs disk and speed cost were not measured.
- Not needed in any tested case: setcap on the helpers, libcap, SYS_ADMIN, `label=disable`, `no-new-privileges` (not set), `seccomp=unconfined`.

### Finding 5: single-uid limitation (E6)

Inside the inner container, root (uid 0) is the only uid. `chown 100:100 /x` fails with `Invalid argument` (rc 1). It is not squashed silently. Per containers-storage.conf(5), `ignore_chown_errors` squashes multiple uids to the default uid in the container, so unpacked files owned by other uids get no such owner (not re-checked in this run). Image groups missing from the single mapping are skipped with `level=warning` lines (`Additional gid=N is not present in the user namespace, skip setting it`). Consequence: images whose files or processes need other uids run their files as root, and processes cannot chown to another uid. Not tested: a process that runs as a non-root image user.

### Finding 6: outer hostname

`--network host` gives the outer container the host's hostname: the E4 probe printed `xserve` after its `unshare -r -u` calls, and the host hostname is `xserve`. The probes used a new UTS namespace, so the host hostname did not change.

### Conclusion

1. FR-062 AC-3: PASS in single-uid mode (E1o, E2, E4c, E5c) with no setcap, no libcap, no SYS_ADMIN, and no subuid or subgid line for the realm user. The stock image with its `useradd` line FAILS (E0). The storage.conf-only form FAILS (E1).
2. "Zero realm image changes" holds only when the realm image has no subuid line for the realm user. The one change in this spike is removing the stand-in's `dev:` lines. CR-007 still applies to that edit. The libcap package conflict with FR-013 (CL-8) does not arise for AC-3 on this path.
3. Single-uid mode is a real limitation (Finding 5). Realm users cannot chown to other uids, and image files owned by other uids become root-owned. ADR-006's "replace the image's useradd line with a range" becomes "remove the line". That change has a usability cost that the SRS does not yet weigh.
4. Setdomainname is not needed for AC-3. The seccomp rule can ungate sethostname alone (Finding 3).
5. This answers the question for podman 5.4.2 and Debian stable only. Whether to adopt single-uid mode, and whether to replace ADR-006's setcap and subuid decisions, is for the user. This spike changes no document.

Follow-ups, not tested:

1. A realm base with no user line for the realm user (the official Debian image has no `dev` user). Expected not to need the `sed`, because keep-id maps uid 1000 with no subuid entry. Not run.
2. An inner container that sets `--domainname` under the sethostname-only profile.
3. Other distributions (Arch, Fedora, Kali) and other podman versions.
4. FR-062 AC-4 (`/dev/kvm`) with this set, and the combined Development set. Run in S-07f (case A; open() only, no ioctl).
5. FR-085 Part B (Docker in a services-on realm). Not run.
6. `--runroot` alone in Finding 1.

#### Conclusion

AC-3 passes in the follow-up setup. A ginn-written `storage.conf` and `containers.conf` in the Realm Home are enough for the plain inner `podman run --rm docker.io/library/alpine:3 true` to exit 0, as uid 1000, with no `--root`, `--storage-opt` or `--storage-driver` flag, and with no setcap, no libcap, no SYS_ADMIN, and no subuid or subgid line for the realm user. The overlay and vfs drivers both pass (E1d, E1d-u2, E1d-vfs, E1d-u2-vfs). The `ignore_chown_errors` key is needed in both drivers (E1d-nokey, E1d-vfs-nokey fail).

The image change is limited to what the realm needs anyway: podman and its helpers installed, and the user created with `useradd -K SUB_UID_COUNT=0 -K SUB_GID_COUNT=0 -m -u 1000 dev`. The `sed` edit in E1d is not needed. ginn must create the realm user with the `-K` override (or otherwise avoid writing subordinate-ID lines for it). A realm user created with plain `useradd` gets `dev:100000:65536`, and plain inner podman then fails with the newuidmap EPERM (E1d-u1).

Points still open:

1. `XDG_RUNTIME_DIR` was unset in the inner environment. A realm that sets it would move the runroot. Not tested.
2. The Realm Home here is the outer container's own `/home/dev`. A Realm Home bind-mounted from a host directory was not tested: its owner and permissions, and whether `keep-id` maps them, may change the result.
3. The single-uid limitation from E6 still applies. E6 was not re-run in the plain setup.
4. The realm image needs podman and its helpers installed. Installing them is outside FR-013's Integration Package Set, and CR-007 covers realm contents. That is a question for the user, not decided here.
5. Only Debian stable with podman 5.4.2 is tested.
