# S-07: nested rootless podman and dockerd inside a Development realm (FR-062, FR-085)

Run: 2026-10-12, Void glibc x86_64, kernel 7.2.9_1, rootless podman 5.8.8, runc 1.5.2 (default OCI runtime; crun not installed), no catatonit on the host. Script: `spikes/s07_nested_containers.sh run` (teardown: `teardown`). Image: `spikes/Dockerfile.s07` (Debian stable 13.7; podman, fuse-overlayfs, slirp4netns, passt, uidmap, catatonit; user `dev` uid 1000). Raw logs in `~/.cache/ginn-spike/s07`, outside the repo. Every host podman call used the spike `--root`, `--runroot` and `--tmpdir` (`/run/user/1000/ginn-spike-s07/libpod-tmp`).

## Verdicts

FR-062 AC-3: PASS
Conditional. `podman run --rm docker.io/library/alpine:3 true` exits 0 inside a services-off outer container only with `--cap-add SYS_ADMIN` and `--device /dev/net/tun` added to the spec base. With the spec base alone (default capabilities) it FAILS (A1, A2, A3). See Decision 1 (NFR-SEC-002).

FR-085: SKIPPED
Part B was not run. `/sys/fs/cgroup/ginn/1000` became user-writable at 11:53 through a root step with S-01's layout (`launch` leaf). That step came from another spike, not this run. The README asks for one spike at a time, so I did not share that tree. Debian stable provides `docker.io` 26.1.5, `rootlesskit` 2.0.2 and `slirp4netns` 1.2.1 as apt packages (no `curl | sh`). Part B still needs a re-run in a serialised window.

FR-062 AC-4 (`/dev/kvm`): FAIL as configured
The realm user and container root both get EACCES on `/dev/kvm`. `--group-add keep-groups` does not help (Finding 9). A host ACL or udev rule is the candidate fix; it needs a root step and was not tested.

NFR-SEC-002: the proposed enumerated set is `SYS_ADMIN` (user-namespace scoped) plus two devices (below). SYS_ADMIN is outside the rootless defaults, so the HLD must enumerate it. This needs a decision (Decision 1).

AS-005: 65536 subordinate IDs is the floor for one nested level, with zero slack. The SRS value of 524,288 is 8x the floor and is sufficient. Host Setup must add a non-overlapping line (Arithmetic).

## Environment facts

- Outer map of this user: `soubarna:100000:65536` in `/etc/subuid` and `/etc/subgid`. Container IDs 0..65536 are mapped (65537 IDs). Container 0 maps to host 100000, container 1000 to host 1000 (keep-id), and the rest to 100000+ (dump in `caps.txt`).
- `/dev/fuse` and `/dev/net/tun` are `crw-rw-rw-`. `/dev/kvm` is `crw-rw----` root:kvm. `soubarna` is in group kvm (24), but gid 24 is not mapped inside any rootless userns.
- `user.max_user_namespaces` = 60183. AppArmor is in the LSM list but not enabled for podman (`AppArmorEnabled=false`). SELinux is absent. Seccomp applies.
- `useradd` in the image writes `dev:100000:65536` into `/etc/subuid`, a range that is not mapped in the outer container (Finding 4).

## Minimal working flag set (Development tier, services off, default seccomp)

Proposed `docs/capabilities.md` section. Shared options are `--userns keep-id --network host --init --init-path <host catatonit>`.

```
podman run -d --name <realm> --userns keep-id --network host \
  --init --init-path <host catatonit> \
  --device /dev/fuse --device /dev/net/tun \
  --cap-add SYS_ADMIN --security-opt unmask=/proc/* \
  <image> sleep infinity
```

- Devices: `/dev/fuse` (required: M2 fails at the overlay mount, fuse-overlayfs is the inner storage driver). `/dev/net/tun` (required for the inner default network, which is pasta; A4 fails without it; not required for `--network host`, N5).
- Security options: `unmask=/proc/*` (required; M3 `unmask=/proc/sys` fails at the proc mount, M4 `unmask=/proc/sys/net` fails at `ping_group_range`, A8 without any unmask fails). `unmask` lifts podman's default masked and read-only `/proc` entries; which of them become writable in the realm was not enumerated. `label=disable` is not required here (M1 passes without it; Void has no SELinux). Keep it only for SELinux hosts. `no-new-privileges` must NOT be set for the Development tier (M5: the setuid helper `newuidmap` fails).
- Seccomp: default profile. `seccomp=unconfined` does not help (A2 fails the same way), so it is not needed.
- Capabilities added beyond the defaults: `SYS_ADMIN` only. The bounding set changes from `0x800405fb` (the 11 default rootless caps: chown, dac_override, fowner, fsetid, kill, setgid, setuid, setpcap, net_bind_service, sys_chroot, setfcap) to `0x802405fb`, a diff of exactly `cap_sys_admin`. Podman also sets ambient and effective SYS_ADMIN for the realm user (`CapAmb`, `CapEff` and `CapInh` = `0x200000`), so the realm shell holds the capability, not only the helper (Finding 2).
- Not usable: `/dev/kvm` (see FR-062 AC-4 above). Not in the set until a Host Setup ACL is tested.
- Inner `/etc/subuid` and `/etc/subgid` must hold a valid range inside the outer map. The working inner value is two lines, `dev:1:999` and `dev:1001:64536` (A6), which give inner 0..65535. The single-range value `dev:1001:64000` (A5) gives inner 1..64000 only.

## Findings

1. Nested `newuidmap` needs CAP_SYS_ADMIN in the outer container's user namespace. A1 and A3 fail with `write to uid_map failed: Operation not permitted`. A4 gets past `newuidmap` and fails only at tun, and A5 passes. The mechanism is consistent with the kernel's `uid_map` write check requiring CAP_SYS_ADMIN over the target namespace. I did not re-check that against kernel source in this spike.
2. The realm user holds SYS_ADMIN, not only the setuid helper. Podman sets ambient caps for non-root `--cap-add`, so `CapEff` and `CapAmb` of the realm user are `0x200000` (dump in `caps.txt`). Narrowing the grant to file caps on `newuidmap` alone was not tested. Podman's ambient handling likely prevents it.
3. Single mapping (no subuid) cannot run alpine: `lchown /etc/shadow: invalid argument` (requested gid 42). A7. So AC-3 needs subordinate IDs, and therefore needs NFR-SEC-002 to allow SYS_ADMIN.
4. The realm image's `useradd` writes `dev:100000:65536` into `/etc/subuid`, which is not mapped in the nested namespace. Any realm image that uses nested rootless podman must overwrite it with a valid range at creation time.
5. Two inner subuid lines work (A6), with inner 0..65535 in one map. This includes inner uid 65534 (`nobody`). A single range from 1001 holds at most 64536 IDs, so `nobody` cannot be mapped with a single range (arithmetic below). I had assumed contiguity was a hard limit. The multi-line result shows it is not.
6. `--network host` for the inner container works with no tun (N5). The inner default network (pasta) and slirp4netns work with tun present (N1, N4). `--network none` works (N3).
7. Default seccomp is sufficient with SYS_ADMIN (A5 and all N and M rows pass with it).
8. An unexplained `podman exec` failure (`nsexec: failed to open /proc/<pid>/ns/user: Permission denied`) hit one exploration container during a manual test sequence. It did not recur in the matrix (no `nsexec` errors in any log), and I did not explain it.
9. `/dev/kvm` in the realm shows as `nobody:nogroup`. The realm user and container root both get EACCES (FR-062 AC-4). `--group-add keep-groups` (on runc, with no crun) leaves the realm user with only `dev`; the host gid 24 is unmapped, so it is dropped. A candidate fix is a Host Setup ACL (`setfacl -m u:<user>:rw /dev/kvm`), which maps through keep-id uid 1000. That is a root step and was not tested.

## Arithmetic (AS-005)

- The outer map has 65537 container IDs (0..65536). Container 0 is the outer root (not exposed to the inner map). Container 1000 is the realm user.
- A full inner range of 65536 IDs (inner 0..65535) needs container IDs 1..65536 except 1000 (inner 0 maps to 1000), i.e. 65536 IDs drawn from `{1..C}` where C is the outer subordinate count. Excluding container 0 requires C >= 65536. Using container 0 would reduce this to C >= 65535.
- So one nested level needs at least 65536 host subordinate IDs for the user, with zero slack. This host has exactly that.
- A single contiguous range cannot give the full 65536. From 1001 the maximum is 64536 (container 1001..65536), so it cannot map inner 65534.
- The SRS value 524,288 is 8x the floor. Every rootless container shares the same map, so this design does not consume it per realm; `--userns auto` style allocation would. It is sufficient.
- Host Setup must write `<user>:<start>:524288` into both `/etc/subuid` and `/etc/subgid`, non-overlapping with existing entries and without changing the existing `soubarna:100000:65536` line. Existing entries on this host: `root:1000:1`, `root:59990:1`, `soubarna:100000:65536`, `act-runner:200000:65536`, `root:1000000:65536`. The block `265536..789823` is free today; Host Setup must compute the start at run time. Untested: whether podman uses both outer ranges (the inner multi-range result suggests it does, same code path). Podman's stored layers also need `podman system migrate` after a subuid change (expected, not tested).

## Part B: Docker in a services-on realm (FR-085): SKIPPED

Reasons: `/sys/fs/cgroup/ginn/1000` was created by a concurrent root step (another spike), so this run did not share that tree (README: one spike at a time). The systemd image is not built.

Expectations, not tested:
- Rootless dockerd via rootlesskit needs newuidmap, so it needs the same SYS_ADMIN (Finding 1).
- slirp4netns needs `/dev/net/tun`.
- Bridge-mode dockerd (rootful inside the realm) with `--network host` (AS-006): creating a bridge needs CAP_NET_ADMIN over the host network namespace, which is owned by the initial user namespace. Even SYS_ADMIN in the realm does not cover it. Expected to fail.

## Decision 1 (for the user, before M6)

Development tier cannot satisfy AC-3 under the NFR-SEC-002 default-caps rule without adding SYS_ADMIN. The options are: (a) enumerate SYS_ADMIN (userns-scoped, and the realm user holds it as effective, not only in the helper) in the HLD set and state the risk; (b) keep the default caps; AC-3 then FAILS, because single mapping cannot run alpine (A7) and no other default-caps path was found. This spike cannot choose between them. I recommend (a) only with the user's explicit approval.
