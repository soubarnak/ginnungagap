# S-09: Kali realm in an isolated pasta netns with NET_RAW (FR-026, FR-027, R-002)

Run: 2026-10-12, host Void Linux glibc x86_64, kernel 7.2.9_1, rootless podman 5.8.8, `rootlessNetCmd=pasta`, slirp4netns installed.
Script: `spikes/s09_kali_netns.sh` (`run`, `teardown`). Image: `docker.io/kalilinux/kali-rolling`, digest `sha256:02f5d6c019e549b0f55da58e835cad5355ef1030c6b2645265a324e37dfc4acc`, built from `spikes/Dockerfile.s09` (nmap, iproute2, iputils-ping, tcpdump; `--no-install-recommends`).
Raw logs stayed outside the repository.

## Verdict

**S-09: PASS**, with two conditions:

1. The stock `nmap` in the Kali image cannot run under `NET_RAW` alone. The image needs a change (see Finding 2). This is not a flag change.
2. A `dummy0` interface exists in the host network namespace and was not removed. Its origin is not established (see Incident). It needs a decision from the user.

FR-027 AC-1: PASS
FR-027 AC-2: PASS

## Environment facts

- Host `podman info`: `rootlessNetCmd=pasta`, pasta at `/usr/sbin/pasta`, slirp4netns at `/usr/sbin/slirp4netns`.
- `/usr/libexec/podman` has no `catatonit`. `--init` was dropped for every run.
- `/proc/sys/net/ipv4/ping_group_range` is `1 0`, so unprivileged ping sockets are disabled.
- Host interfaces before and during the spike: `lo`, `eno1` (192.168.0.121/24, UP), `wlp4s0` (DOWN), `virbr0` (DOWN).
- The image has no `python3`, `ncat`, `nping`, `getcap`, `setcap` or `iw`. Perl core is present.

## Procedure deviations

- `--init` dropped (no catatonit on host). Roadmap line 40 keeps `--init --init-path /usr/bin/catatonit` in the product argv. That form was not tested here.
- Stock `/usr/bin/nmap` fails at exec under the proposed flags. Every nmap SYN/ACK result below comes from a copy of `/usr/lib/nmap/nmap` made with `cp` inside the container. `cp` does not copy the file-capability xattr (Finding 2).
- `-Pn` added to every nmap run, so host discovery cannot skip the scan.
- Port-forward server: perl core sockets (no python3 or ncat in the image).
- The `iw dev` probe was run, but `iw` is not in the image (rc 127). Host-interface monitor mode was tested with `ip link set wlp4s0 type monitor`.

## Findings

1. **Raw sockets work in the isolated realm (FR-027 AC-1).** Root in the realm holds `cap_net_raw`. AF_PACKET capture works (tcpdump). Raw ICMP socket creation works (ping sends, no EPERM). The copied nmap runs SYN scans (loopback and example.com). Raw sockets do not work in the shared host netns (B), even with `NET_RAW`.

2. **Stock nmap cannot run with `NET_RAW` alone.** `/usr/lib/nmap/nmap` fails at exec with EPERM under A, A0, B and S. A copy made with `cp` runs. C (with NET_ADMIN in the bounding set) runs the stock binary. Conclusion: the binary carries file capabilities that need NET_ADMIN in the bounding set. `getcap` is not in the image, so the xattr itself was not read. Fix candidate: strip file capabilities from `/usr/lib/nmap/nmap` at Kali image build (`setcap -r`, which needs libcap2-bin). This was not tested. The argv does not change.

3. **ICMP echo does not work.** `ping 1.1.1.1` gets no reply. The likely cause is `ping_group_range = 1 0`, which disables the ICMP echo relay in pasta. Not verified. Kali help must say so.

4. **TCP probes are answered by the relay (R-002).** Pasta and slirp4netns complete TCP through host sockets. Example.com SYN returned open and ACK returned unfiltered. The SYN-ACK TTL was 255 under pasta and 64 under slirp4netns, which suggests the relay generated the reply. Host-side capture was not done, so this is not proven. For 192.168.0.250, a live LAN device that answered ARP, the realm got no reply for port 80, and the host's own connect failed with "No route to host". The relay did not invent a RST. The result: SYN and ACK scans from a Kali realm report the relay's connection result, not the target's raw TCP behaviour.

5. **`--network pasta:-t,8080` exposes the realm on all host addresses.** P1 answered on 127.0.0.1 and on the LAN address. `-p 127.0.0.1:8081:8081` (P2) binds loopback only. Use the loopback publish for Kali services.
   A first P1 attempt returned "Empty reply". The cause was my test server closing the socket with unread request bytes (RST). The server was fixed to read the headers first, and P1 then passed. The failure was in the test server, not in pasta.

6. **NET_ADMIN inside the realm stays in the realm (C).** `dummy0` and `eno1 down` worked inside the realm. The host NIC stayed UP. The SRS grants NET_RAW only, so keep NET_RAW only.

7. **Shared netns (B) exposes host interfaces and blocks raw sockets.** `ip -br link` lists host interfaces. Rootless root has no NET_RAW in the initial user namespace, so `--cap-add NET_RAW` does nothing for `--network host`. Changes are denied (`lo down`: EPERM). That is why Kali needs the isolated netns.

8. **AC-2 mechanism.** In the isolated realm, host interfaces are not visible (`wlp4s0` not found). Changes to realm devices are denied with EPERM when NET_ADMIN is absent. In the shared netns, changes are denied by EPERM alone.

## Incident: host `dummy0` (unresolved)

- A `dummy0` (MAC d6:a4:56:35:7a:08) exists in the host netns. Its sysfs node was created at 11:41:28.38, during the first attempt of this spike, in the same second as that attempt's Run C.
- The spike did not intend to create it. Run C's `ip link add dummy0 type dummy` returned 0 in the realm, and realm `dummy0` (different MAC) was visible inside the realm. One `ip link add` creates one device in one netns, so the realm add made the realm device.
- Later runs confirmed the host-side add does not happen. A realm `ip link add dummy0` returned 0 while the host `dummy0` existed. In the host netns that call would fail with EEXIST.
- Origin not established. It may come from another process or agent active on the host at that time. Removing it needs root (`ip link` needs CAP_NET_ADMIN in the initial netns), which this spike does not use.
- Action needed: `sudo ip link del dummy0` if the device is not wanted. Confirm whether another spike or agent created it.

## Recommendation

**Argv (tested form, Run A):**

```
podman run -d --name <realm> --userns keep-id --user 0:0 \
  --network pasta --cap-add NET_RAW \
  <kali-image> sleep infinity
```

Product additions (not tested here; catatonit is absent on this host):

- Services off: add `--init --init-path /usr/bin/catatonit` (roadmap line 40).
- Services published to the host: `-p 127.0.0.1:<hostport>:<realmport>` (tested as P2). Do not use `--network pasta:-t,<port>`, which binds every host address.
- Kali image build: remove file capabilities from `/usr/lib/nmap/nmap` (Finding 2). This needs a build step and a decision on whether libcap2-bin joins the image.

**Helper choice:** pasta, per FR-026 and the roadmap wording. TCP and publish behaviour matched slirp4netns in these tests. The cost is about 16.4 MiB RSS per realm against about 3.0 MiB for slirp4netns. If the NFR-002 budget counts helper RSS per realm, slirp4netns is the candidate. That is a user decision.

**Kali TOML / `docs/capabilities.md`:** list `NET_RAW` as the only added capability. `NET_ADMIN` is not needed.

**R-002 limitation text (OOS-9), for Kali help:**

> Kali realms run in their own network namespace. TCP leaves the realm through a host relay that opens its own connections. Raw packets do not leave the realm, so SYN and ACK scans of other hosts report the relay's connection result, not the target's raw TCP replies. ICMP echo to other hosts does not work. For reachability checks, use connect scans (`nmap -sT`). Services in the realm reach the host only through ports published on 127.0.0.1.
