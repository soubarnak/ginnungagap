## 4. Escalations (design decisions, not changed here)

ADR-008 says a negative gate result is escalated and not accepted. Nothing here changes the ADRs.

### 4.1 ADR-008: a file grant with an open descriptor gives EBUSY under plain `umount2`

- Measured: `umount2` without `MNT_DETACH` on `/run/user/1000/ginn-hold-file`, with an open descriptor in the container, gives EBUSY. The helper exits 1, and the re-attach fails with `GINN-E-ATTACH-FAILED`. The old file stays mounted.
- The directory control (section 2) also gives EBUSY under plain `umount2`, so the directory case already needs `MNT_DETACH`, as the ADR says.
- Socket grants with a connected client did not give EBUSY. The case of an O_PATH descriptor on the socket path was not measured.
- ADR-008 says: if this fails, `MNT_DETACH` applies to every re-attach, and the amendment is changed to say so. The measured file case is the failure that clause names. The decision is open.

### 4.2 ADR-008 drive case: a host-namespace mount after the pause process is not seen by `podman unshare`

- Measured: a FUSE drive mounted on the host after the store's pause process existed is in the host mount table (`host_mountinfo_has_drive: true`), and not in `podman unshare`'s namespace (`NOT_SEEN`). A mount made in the store namespace is seen (PASS, store-namespace control).
- The host root mount is private. `/proc/self/mountinfo` has `/` with no optional peer-group field, and podman warns `"/" is not a shared mount`. The helper runs in the store's namespace, which the pause process holds. A host mount made after the pause exists did not reach it. This matches the ADR-008 rule that private mounts stay private in a less privileged user namespace. The kernel source was not checked for the mechanism.
- The sharpest consequence: after the re-attach ran (rc 0, one record, the new identity recorded), `needs_reattach` returns **False**. The record says the drive is attached, the realm cannot see it, and nothing retries until the host identity changes again. This is the failure in one sentence, and it is not only a missed attach.
- ADR-008 T4.9 notes say this is FAIL, escalated, and not accepted.
- Options for the decision (not chosen here): make the store namespace follow host mounts (shared propagation on the host root, which is not the Void default), recreate the pause when a mount root changes, or move the drive attach to a path the helper can reach from the host side. Whichever is chosen must also stop the pre-check from recording a grant as attached when the realm does not see it.

### 4.3 podman 5.8.8: `--passwd=false` is not a `podman create` flag, and keep-id always writes the entry

- Measured: `podman create --passwd=false` exits 125 (`unknown flag: --passwd`). `podman create --help` has `--passwd-entry` only. `podman run --help` has `--passwd`.
- `runtime/spec.py` (`passwd=False`) and `podman/adapter.py` (`--passwd=false`) build the argv the realm create uses. On this podman, every real `ginn create` fails at the `created` step with exit 125, before any user step. The create is not usable as written. This is an assumption of the T4.4 review that podman 5.8.8 does not meet.
- Dropping the flag does not fix it. Keep-id then writes the passwd entry (uid 1000, name `soubarna`) and the group entry at create time, and the realm `useradd` exits 9 (the name clash). Four keep-id argv variants were checked (plain, no `--user`, `keep-id:uid=...,gid=...`, `--passwd-entry`). Each writes a passwd entry for uid 1000. The `--passwd-entry` variant writes the entry given to it. A probe with `--passwd-entry 'soubarna:x:1000:1000::/home/soubarna:/bin/sh'` wrote exactly that line, so `--passwd-entry` is a measured option for the decision.
- The injected home is `/` unless the create spec sets `HOME` (the ctl2 realm got `/`). A probe with `-e HOME=<host home>` got the host home. So the spec's environment decides the realm user's home.
- Options for the decision: (a) accept the injected entry when its uid and name match the host user, and drop the useradd step; (b) keep the step and make it tolerate an entry with the same uid and name; (c) write the entry with `--passwd-entry` and make the step check it; (d) another mechanism for the realm user. Each is an ADR-level change (ADR-006 and `docs/capabilities.md` name the `useradd` step; the T4.4 review wrote the flag).
- Not changed: `runtime/spec.py` and `podman/adapter.py` keep `passwd=False`, and `ops/create.py`'s user step is unchanged.
- The gate realm was built with `_PasswdTrue` (the create argv with `passwd=True`, so no flag is sent) and with the user step skipped (`_skip_user_step`). Its user is the entry podman injected (`soubarna`, uid 1000). This is a test-only seam, and the rest of the gate depends on that realm.

## 7. Resolution A

Dated 2026-10-13. This section decides the two escalations of sections 4.1 and 4.2. Sections 1 to 6 keep the run of the gate as it was reported. ADR-008 amendment "Resolution A" carries the decisions, and this section carries the evidence.

Decision on section 4.1 (`MNT_DETACH`): every re-attach detaches with `MNT_DETACH`. The ADR's own clause applied, since plain `umount2` gave EBUSY on the file grant with an open descriptor. The file case now passes, and the realm reads the new contents (`h-v2`).

Decision on section 4.2 (the drive): the drive case works, by variant (c). The helper runs on the host, joins the realm's user namespace, copies the host mount table, clones the sources from that copy, then joins the realm's mount namespace. The brief expected the cross-namespace `move_mount` to be refused. It was not. The probes measured every call:

| Probe | Steps and errno | Result |
