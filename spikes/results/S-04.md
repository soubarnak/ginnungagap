# S-04: runtime root across logout (CL-1, ADR-004)

Status: the real-logout run below is invalid. The simulated logout (S-04s, the last section) gives the verdicts for CL-1.

Run: 2026-10-12, Void glibc x86_64, kernel 7.2.9_1, rootless podman 5.8.8, crun 1.30.1, elogind 1021 (pid), uid 1001 for the throwaway user `ginn-spike`. Script: `spikes/s04_s08_logout.sh` (subcommands in its header). Raw logs, including `root-commands.log`, are in the session scratchpad, outside the repository. The control socket for ssh lived in `~/.cache/ginn-s04-ctl` (removed).

## Verdict

S-04: invalid: no elogind session.

The precondition failed. An ssh login as `ginn-spike` did not register with elogind, so `/run/user/1001` was never created. The logout test measured nothing about variant A or variant B. No container was started, so no `podman` storage was created. Per the brief, the run stopped and was cleaned up.

## Precondition evidence

- PAM stack: `/etc/pam.d/sshd` includes `system-remote-login`, which includes `system-login`. `system-login` has `-session optional pam_elogind.so`. `/usr/lib/security/pam_elogind.so` is present. `pam_turnstile` and `pam_dumb_runtime_dir` are not in use.
- The sshd session did open a PAM session. `/var/log/socklog/secure/current` has `pam_unix(sshd:session): session opened for user ginn-spike(uid=1001)`. Inside the login, `/proc/self/loginuid` is 1001 and `/proc/self/sessionid` is 4.
- Inside the login: `XDG_SESSION_ID` unset, `XDG_RUNTIME_DIR` unset, `/run/user/1001` absent. `/proc/self/cgroup` showed `1:name=elogind:/` and `0::/2`.
- `loginctl list-sessions` inside the login listed only `2 1000 soubarna seat0 tty7`. The ginn-spike session was not listed.
- Two login styles were tried. One was a ControlMaster connection without a pty. The other was `ssh -tt` (`/dev/pts/2`) on a separate connection. Both failed the same way.
- pam_elogind wrote no error for the sshd sessions. The only pam_elogind error on record is from 2026-10-10 (greetd: system bus unreachable).
- `/run/systemd/system` does not exist. This is observed only. It was not verified as the cause.
- `KillUserProcesses`: `/etc/elogind/logind.conf` line 16 is `#KillUserProcesses=no`, commented, so the default (no) applies.
- Finding for the procedure: sshd opens and closes a PAM session per channel command (`Starting session: command` and `Close session` for each `ssh` command in `sshd.log`). One ControlMaster connection is therefore not one PAM session. Each `rx` call is its own session.

## Simulated logout (S-04s/S-08s)

Run: 2026-10-12, same host, same kernel, rootless podman 5.8.8, crun 1.30.1, as uid 1000 (the user's own session, no root, no sudo). Scripts: `spikes/s04s_s08s_sim.sh` (procedure; subcommands in its header), `spikes/s04s_s08s_uclient.c` (probe client), `spikes/s04s_s08s_rebind.py` (socket rebind helper, also used in S-08.md). Raw logs (command log with the exact podman argv, per-step output, the debug log of the first variant B call, pinned process list) are in the session scratchpad, outside the repository, in `s04s-final/`. `s04s/` holds an earlier run of the same procedure (see Run history).

### What this simulates, and what it does not

This is a simulation of elogind's runtime-directory removal at the last logout. It is not a real logout. The ssh login path does not register an elogind session on this host (see the invalid sections above), so the real PAM session teardown was not measured, and no PAM or elogind setting was changed.

- `$SIM_RUNTIME = /run/user/1000/ginn-spike-s04sim` stands in for `/run/user/<uid>`. "Logout" is `rm -rf` of that directory after a path check. "Login" recreates it empty, mode 0700. The directory is a plain subdirectory of the real `/run/user/1000` tmpfs, so nothing is unmounted.
- `$SIM_GINN = /dev/shm/ginn-spike-s04sim-ginn` stands in for the ginn runtime root. It is not removed at logout. Both stand-ins live on tmpfs (`/dev/shm` and `/run/user/1000`). tmpfs contents are always lost at a reboot, so a reboot clears both. What was meant: the simulated logout removes only `$SIM_RUNTIME`, and nothing in it touches `$SIM_GINN`, so `$SIM_GINN` survives every simulated logout within one boot. Its survival through a real logout (elogind teardown) is not tested.
- KillUserProcesses is unset (`/etc/elogind/logind.conf` default: no), so no process is killed at the simulated logout.
- The socket server for S-08s is stopped at logout, as the brief asked.

Not covered: the real PAM session close, elogind session and scope teardown, and the unmount of the runtime tmpfs. Hosts with `KillUserProcesses=yes`, or a user manager that stops units at logout. Cgroup scope removal (every container here used `--cgroups disabled`). Networking (`--network none`). The `/run/ginn/<uid>` path that ADR-004 would use (this run used `/dev/shm`).

### Layout and procedure

Two containers, both `docker.io/library/alpine:3` running `sleep infinity`, started with `--runtime crun --cgroups disabled --network none`. Each variant has its own `--root` (separate stores, loaded from the same image tar), so the variants never share a database:

- Variant A: `env XDG_RUNTIME_DIR=/dev/shm/ginn-spike-s04sim-ginn podman --root $HOME/.cache/ginn-spike-s04sim/a/root --runroot /dev/shm/ginn-spike-s04sim-ginn/podman --tmpdir /dev/shm/ginn-spike-s04sim-ginn/tmp --runtime crun`
- Variant B: `env XDG_RUNTIME_DIR=/run/user/1000/ginn-spike-s04sim podman --root $HOME/.cache/ginn-spike-s04sim/b/root --runroot /run/user/1000/ginn-spike-s04sim/podman --tmpdir /run/user/1000/ginn-spike-s04sim/tmp --runtime crun`

Sequence: `start` (containers, gen1 server, pins), `logout`, 15 s wait, pin check, `login`, pin check, first variant B call with `--log-level=debug`, `inspect`, `exec`, `stop` for each variant, `reap`, `teardown`. Every pinned process is recorded by pid, start time and command line. A kill is sent only when all three still match, so a reused pid is never signalled. Unpinned leftovers (podman's pause processes) are matched by their exact `XDG_RUNTIME_DIR` or by a conmon command line that names the spike's paths; a shell whose command text only mentions a path is never matched. No `podman` call omits the three storage flags, and none runs without them.

### Results

| | before logout | after logout and 15 s | after login, before any podman call | first podman call after login |
|---|---|---|---|---|
| `s04a` (A) | running | sleep and conmon alive | alive | `ps -a` running, `exec` rc 0, `stop` rc 0 |
| `s04b` (B) | running | sleep and conmon alive | alive | state refresh: `exited`, pid 0; `exec` rc 255; `stop` rc 0 with no effect; `rm -f` rc 0, orphan survives |

Evidence:

- Variant A: after the logout, `podman ps -a` shows `s04a` and `s08c` running. `exec` prints `exec-ok`. `stop` logs `StopSignal SIGTERM failed to stop container s04a in 2 seconds, resorting to SIGKILL`, because the container's PID 1 did not exit on SIGTERM. The alive files in `$SIM_GINN/tmp` (`alive`, `alive.lck`) survive the logout.
- Variant B, first call after login: the debug log shows `Podman detected system restart - performing state refresh`, then `level=error ... Refreshing container f4711b6c...: acquiring lock 6 ...: file exists`. Before that call, `$SIM_RUNTIME` held only the socket, so B's `tmp/alive` file was missing. That is consistent with podman's restart check, which looks for the alive file in the tmpdir (not verified in podman's source). After the call, `alive` and `alive.lck` exist in B's `tmp`. The "file exists" error was not traced further.
- Variant B orphans: the `sleep infinity` processes and their conmon kept running through the logout, the login, and the podman calls. `podman stop` returned 0 and changed nothing. `podman rm -f` returned 0 and the orphan survived. The orphans were killed by pid: they did not exit within 3 s of SIGTERM, and SIGKILL stopped them.
- Rootless pause processes (`podman`, ppid 1) stayed alive through the logout and the checks, one per variant store. Podman calls in `reap` and `teardown` (`rm -f`, `unshare`) started more of them. `reap` and `teardown` killed them by pid.

S-04s: PASS (A), FAIL (B), simulated. A stays manageable after the simulated logout. B's containers read as exited while their processes run, and only a pid-level kill frees them.

Verdict S-04s (simulated):

- A: PASS. The runroot and tmpdir under the simulated ginn root survive a logout that removes the session directory. Containers stay running, visible, exec-able and stoppable with the same flags.
- B: FAIL. Runroot and tmpdir under the session directory are removed with it. At the first podman call after login, podman assumes a reboot, refreshes its state, and reports the containers as exited while the processes still run. `exec` is refused, `stop` and `rm -f` do not reach the processes, and only a pid-level kill frees them.
- Design consequence for ADR-004 (not decided here): the ginn runroot and tmpdir must live outside the per-login runtime directory. That matches the variant A layout in the plan (`/run/ginn/<uid>`, created at Host Setup). This run used `/dev/shm` instead.
- Prediction, not tested: the user's default store keeps its runroot at `/run/user/1000/containers` and its tmpdir at `/run/user/1000/libpod/tmp` (both visible in the argument list of the running `bb-pg` conmon). That is the variant B layout, so a real logout would produce the same state there. The S-02 and S-06 notes contain no bb-pg incident record (S-01 only says bb-pg was not touched), so no comparison with a past incident was made. No command was run against the default store.

Cleanup: `reap` removed `s04a`, `s08c` (with `podman rm -f`) and `s04b`, then killed the pinned leftovers. `teardown` ran `podman unshare rm -rf` with the three flags for each root. Both reported `Device or resource busy` on the `overlay` directory, because the rootless overlay self-bind mount lives in the unshare's own mount namespace. The plain `rm -rf` fallback then removed the roots after an ownership check (every entry owned by uid 1000) inside the `ginn-spike-s04sim` paths. Final check: no spike directories, no mounts naming the spike, no spike processes.

### Run history

- `s04s/` (13:30 to 13:38): the same procedure. Its S-08 rebind helper failed at step 3 with ENOENT. The cause was a helper bug: it read `/proc/self/status` after `setns(mnt)`, and in the container's mount namespace `/proc/self` does not resolve. The setns itself had succeeded. The helper was fixed and the full sequence was rerun as `s04s-final/`. S-04s results were the same in both runs.
- `s04s/`, teardown: after the teardown of this run, two rootless pause processes stayed behind: pid 11888 (variant A, `XDG_RUNTIME_DIR=/dev/shm/ginn-spike-s04sim-ginn`) and pid 11927 (variant B, `XDG_RUNTIME_DIR=/run/user/1000/ginn-spike-s04sim`). Both had ppid 1 and command line `podman`. Before signalling each one, the check confirmed uid 1000, the exact `XDG_RUNTIME_DIR` value, and the command line. Both were sent SIGTERM and were gone after 2 s. The script then gained `kill_leftovers`, which runs before the owner-checked `fallback_rm` in `teardown`. This manual kill is the only cleanup step done outside the script.
- `s04s-final/`, teardown: the first teardown attempt refused to run, because the shell that ran it had the spike paths in its command text and the first process-matching rule matched that shell. The rule was narrowed to exact `XDG_RUNTIME_DIR` values and to conmon or server command lines (the current script). Teardown was then rerun and completed. The narrower rule is what the commit contains. No process was signalled in that step.
