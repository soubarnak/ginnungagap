Collected 2026-10-12 (UTC). Requirements: FR-011, FR-013, DR-040, DEP-4, IR-021, AS-024, R-003.
Script: `spikes/s10_image_channels.sh` (prints the TOML fragment). Output: `src/ginn/trust/data/trust.toml` v1.

Method: registry API only (skopeo, curl, openssl). Network limited to registries. No image was pulled. The task rule is "do not pull full images unless skopeo inspect is unavailable", and skopeo is installed, so no pull was made. Uncompressed sizes come from a 4-byte range read of each gzip layer (ISIZE trailer). No podman storage was created, so the spike root was not used and nothing needed cleaning.

### Arch quay.io: what was verified

Verified locally against the registry bytes:
- The signature layer's payload blob hashes to its layer digest (`f215f19d...`).
- The payload `critical.image.docker-manifest-digest` equals the pinned platform digest `c556b483...`.
- The payload's `critical.identity.docker-reference` is `quay.io/archlinux/archlinux:base-20261011.0.609834`. It names a dated tag, not `:base`.
- The ECDSA signature (`dev.cosignproject.cosign/signature`) verifies with the public key of the leaf certificate embedded in the `dev.sigstore.cosign/bundle` annotation.
- The leaf certificate is keyless (Fulcio). It is issued by `O=sigstore.dev, CN=sigstore-intermediate`, with validity 2026-10-11 09:11:35 to 09:21:35 UTC.
- The certificate identity (SAN URI) is `https://gitlab.archlinux.org/archlinux/archlinux-docker//.gitlab-ci.yml@refs/tags/v20261011.0.609834`. The OIDC issuer extension is `https://gitlab.archlinux.org`.
- The Rekor transparency log entry is logIndex `3204386378`, integratedTime `1791709905` (2026-10-11).

Not verified (no cosign binary, and the chain and log are outside the registries-only network):
- The Fulcio chain to the sigstore root of trust (needs the TUF root, which is not a registry).
- Rekor inclusion proof and signed-entry timestamp.
- That the identity pattern above is the one Arch publishes as its signing policy.

Consequence for T2.14: match the signature to the pinned digest, not to the tag string. The signed reference is the dated tag.

## 5. Integration Package Set (FR-013)

Host `LANG` on this machine is `en_US.UTF-8`. The Integration Package Set must supply locale data for that value.

What the registry metadata shows about the base images (no layer read):
- Arch (quay and Docker Hub): config `ENV LANG=C.UTF-8`. Build history is a `COPY` of a rootfs plus `ldconfig` and `os-release` edits. No package install is recorded.
- Debian: one build-history entry, `debian.sh --arch amd64 ... 'stable'` (debuerreotype). No package list is recorded.
- Fedora: built with KIWI 11.1.1. No package list is recorded.
- Kali: config `ENV LANG=C.UTF-8`, with a single rootfs layer. No package list is recorded.

So whether `ca-certificates` or locale data are already present in each base image is **not verified**. It needs one pull per distro, or a layer read, both excluded by the task's network rule.

Proposed sets, with what is and is not verified:

| Distro | Proposed `integration_packages` | Verified | Open for M4 |
|---|---|---|---|
| Arch | `ca-certificates` | no | No locale package was identified. Locale data would come from glibc's `locale-gen` for `en_US.UTF-8` (needs `/etc/locale.gen`). Package-name check against the Arch repos needs network outside the registry rule. |
| Debian (stable-slim) | `ca-certificates`, `locales` | no | `locales` needs a locale-generation step for `en_US.UTF-8` after install (`locale-gen`), not only the package. |
| Fedora (44) | `ca-certificates`, `glibc-langpack-{lang}` | no | `{lang}` is `en` for the host `LANG` (`en_US.UTF-8`). Langpack names are not checked against the Fedora repos. The `glibc-langpack-{lang}` naming is a proposal, not a verified package list. |
| Kali (rolling) | `ca-certificates`, `locales` | no | Same as Debian. |

Image-level exclusions are the M4 risk that matters most. Each of these can make the packages install while the locale data never lands:
- Arch: `NoExtract` lines in `/etc/pacman.conf`.
- Debian slim: `path-exclude` rules under `/etc/dpkg/dpkg.cfg.d/`. The key question is whether `/usr/share/i18n` and the `en_US` locale sources survive.
- Fedora: `tsflags` in `/etc/dnf/dnf.conf`, and `%_install_langs` in `/etc/rpm/macros*`. Fedora images may restrict installed languages.

None of these was read. The test that closes this item is a pulled image plus `pacman -Q`, `dpkg -l` and `rpm -qa` after `podman run --rm --network none`, and a check that an `en_US.UTF-8` locale resolves (`locale -a`).

## 6. Proposed Trust Manifest refresh procedure

Manual sequence, run on a host with skopeo, curl, jq and openssl. Dev-time only, not part of ginn at runtime. T2.14 will script it as `tools/refresh-trust-manifest.py`.

1. For each distro, read the x86_64 platform digest:
   ```sh
   skopeo inspect --raw docker://<repo>:<tag> | jq -r '.manifests[] | select(.platform.os=="linux" and .platform.architecture=="amd64") | .digest'
   ```
   If the image is a single manifest (Arch on quay), the platform digest equals the index digest.
2. Confirm the signature for Arch on each refresh: the `sha256-<platform>.sig` tag exists, its payload `docker-manifest-digest` equals the new platform digest, and cosign verifies the keyless bundle against the Arch CI identity. Verify the Fulcio chain and Rekor inclusion with cosign and the Sigstore TUF root. This step is needed once per refresh, not in ginn.
3. Re-run `spikes/s10_image_channels.sh <repo:tag>...` for the sizes and the signature facts.
4. Edit `src/ginn/trust/data/trust.toml` for the changed distros only: `digest`, the two sizes, `signature`, and `verified_on`. Change `image` only when the channel changes (for example `fedora:44` to `fedora:45` once 45 is GA). Change `integration_packages` only when the set changes.
5. Check the file parses and every digest has the form `sha256:` plus 64 hex characters (the T2.14 test).
6. Host test: `podman pull <image>@<digest>` and the Integration Package Set check, on a Void host.
7. Commit `trust.toml` and cite the refresh in the commit message (FR-011, DR-040).

How often (a proposal for the ADR, not decided here):
- Arch: the quay channel builds several times a week (tag history shows near-daily `base-2026…` tags). A refresh every two weeks, and before any release, keeps the base within a few days of current.
- Debian: after each Debian point release, and at least monthly for the rebuilt stable image.
- Fedora: when Fedora 45 reaches GA, `latest` moves to 45 and the pin should follow. Check the registry for `latest` monthly, and refresh on the first change.
- Kali: rolling, so monthly. Also at each Kali release if the channel changes.

How the pinned digest relates to AS-024 and R-003:
- trust.toml pins one digest per distro. FR-011 allows only that digest, so a new realm always gets the pinned base. The pin is the ceiling for new realms.
- The "base is upgraded on first update" mitigation (R-003) means: when a refreshed trust.toml ships, an existing realm moves to the new digest the first time it is updated. That update goes through FR-023 and verifies the new digest. The mechanism is a proposal for the ADR.
- AS-024 says a realm tracks the current stable release at creation. The `stable` and `44` tags mean that at refresh time. Moving to a new major release is a rebuild (FR-021), not an in-place update, so the release tag in `image` is only changed at a refresh.
- The digest is verified, never the tag. A tag that moves between refreshes does not change what ginn accepts.

## 7. Open items

These do not change the verdict, which only requires a resolvable x86_64 digest per distro. They are M4 verification items.
1. One pull per distro, by digest, into the spike root (`podman --root ~/.local/share/ginn-spike-s10/podman --runroot $XDG_RUNTIME_DIR/ginn-spike-s10`). Measure `podman image inspect .Size`, read `/etc/os-release` (the Debian codename behind `stable`, the Fedora release), and query `ca-certificates` and locale packages. Blocked by the task's no-pull rule. The task's "do not pull" rule and its "if you can, pull ONE image" wording conflict. One pull per distro closes sections 5 and 7 and needs an explicit go-ahead from the parent.
2. Fedora: is dnf present in `fedora:44`, and is it absent from `fedora-minimal:44`? This decides between the two. It needs a layer read, so it is open.
3. Image-level packaging exclusions (section 5): pacman `NoExtract`, dpkg `path-exclude`, dnf `tsflags` and `%_install_langs`. Not read.
4. Fedora GPG signing: source unknown. Debian Docker Content Trust: not probed.
5. Cosign verification of the Arch bundle to the Fulcio root and Rekor inclusion (needs the TUF root).
6. Kali channel: AS-024 covers only Debian and Fedora. The SRS author decides rolling versus last-release.
7. Fedora 45 GA: `45` exists on both registries and `latest` is 44. Whether 45 is GA was not verified (not a registry). If 45 is GA, the pin is one release behind until it is refreshed.
