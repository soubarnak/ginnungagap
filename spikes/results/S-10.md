# S-10: image channels, digests, sizes and signatures for the Trust Manifest (R-003)

Collected 2026-10-12 (UTC). Requirements: FR-011, FR-013, DR-040, DEP-4, IR-021, AS-024, R-003, NFR-008.
Script: `spikes/s10_image_channels.sh` (prints the TOML fragment). Output: `src/ginn/trust/data/trust.toml` v1.

Method. Sections 1 to 6 use registry metadata only (skopeo, curl, openssl). The script pulls nothing. Uncompressed sizes come from a 4-byte range read of each gzip layer (ISIZE trailer). Section 7 (S-10b) pulls the recommended images by pinned digest into a dedicated storage root, measures them, runs the in-image checks, then removes the storage. The task rules were that the spike storage root is always passed explicitly, and that full pulls happen only with the coordinator's go-ahead.

Not verified (no cosign binary, and the chain and log are outside the registries-only network):

Image-level exclusions read from the pulled images:
- Arch: `/etc/pacman.conf` `NoExtract` excludes `usr/share/locale/*` and `usr/share/i18n/*`, with negations that keep the `en_US` locale sources. The `en_US` sources were confirmed present, so generation works (section 7).
- Debian slim: `/etc/dpkg/dpkg.cfg.d/docker` has `path-exclude /usr/share/locale/*`. That removes message catalogues only. Locale data lives under `/usr/lib/locale`, which this rule does not exclude.
- Fedora minimal: `/etc/dnf/dnf.conf` has `tsflags=nodocs`. `/etc/rpm/macros.image-language-conf` sets `%_install_langs en_US`. A host `LANG` of `en_US` is fine. Any other host `LANG` would have its langpack files filtered out, so the packages install but no locale data lands (M4 item: override `_install_langs` for the Integration set).
- Kali: no path-exclude rules in the image.

## 6. Proposed Trust Manifest refresh procedure

Manual sequence, run on a host with skopeo, curl, jq and openssl. Dev-time only, not part of ginn at runtime. T2.14 will script it as `tools/refresh-trust-manifest.py`.

1. For each distro, read the x86_64 platform digest:
   ```sh
   skopeo inspect --raw docker://<repo>:<tag> | jq -r '.manifests[] | select(.platform.os=="linux" and .platform.architecture=="amd64") | .digest'
   ```
   If the image is a single manifest (Arch on quay), the platform digest equals the index digest.
2. Confirm the signature for Arch on each refresh: the `sha256-<platform>.sig` tag exists, its payload `docker-manifest-digest` equals the new platform digest, and cosign verifies the keyless bundle against the Arch CI identity. Verify the Fulcio chain and Rekor inclusion with cosign and the Sigstore TUF root. This step is needed once per refresh, not in ginn.
3. Re-run `spikes/s10_image_channels.sh <repo:tag>...` for the sizes and the signature facts.
4. Pull each changed image by its new digest into a throwaway storage root, record `podman image inspect --format '{{.Size}}'`, run the package checks in section 7, then remove the storage root.
5. Edit `src/ginn/trust/data/trust.toml` for the changed distros only: `digest`, the sizes, `signature` (Arch stays `sigstore-unverified`, see section 3), `measured_installed_bytes` and `verified_on`. The Integration Package Set is in the distro TOML (R9), not here. Change `image` only when the channel changes (for example `fedora-minimal:44` to `fedora-minimal:45` once 45 is GA).
6. Check the file parses and every digest has the form `sha256:` plus 64 hex characters, with `digest_kind = "platform"` (the T2.14 test).
7. Host test: `podman pull <image>@<digest>` and the Integration Package Set check, on a Void host.
8. Commit `trust.toml` and cite the refresh in the commit message (FR-011, DR-040).

How often (a proposal for the ADR, not decided here):
- Arch: the quay channel builds several times a week (tag history shows near-daily `base-2026…` tags). A refresh every two weeks, and before any release, keeps the base within a few days of current.
- Debian: after each Debian point release, and at least monthly for the rebuilt stable image.
- Fedora: when Fedora 45 reaches GA, `latest` moves to 45 and the pin should follow. Check the registry for `latest` monthly, and refresh on the first change.
- Kali: rolling, so monthly. Also at each Kali release if the channel changes.

How the pinned digest relates to AS-024 and R-003:
- trust.toml pins one digest per distro. FR-011 allows only that digest, so a new realm always gets the pinned base. The pin is the ceiling for new realms.
- The "base is upgraded on first update" mitigation (R-003) means: when a refreshed trust.toml ships, an existing realm moves to the new digest the first time it is updated. That update goes through FR-023 and verifies the new digest. The mechanism is a proposal for the ADR.
- AS-024 says a realm tracks the current stable release at creation. The `stable` and `44` tags mean that at refresh time. Moving to a new major release is a rebuild (FR-021), not an in-place update, so the release tag in `image` is only changed at a refresh.
- The digest is verified, never the tag. A tag that moves between refreshes does not change what ginn accepts. S-10b confirmed that a pull by digest yields a local image whose digest equals the pinned value, for all five pulled images.

Findings:
- **Digest pull path works.** All five images were pulled by the pinned platform digest, and the local digest equals it. That proves the FR-011 digest-pull path with these digests.
- **Debian codename.** The `stable-slim` tag is trixie (Debian 13) in this image. `stable` (full) was not pulled. It is built from the same `stable` suite at the same SOURCE_DATE_EPOCH as `stable-slim`, so it is very likely trixie too (not verified).
- **Kali version.** The rolling image reports VERSION_ID 2026.3, while its label version is 2026.10.11.
- **Arch.** `ca-certificates` 20240618-1 and `ca-certificates-mozilla` 3.131-1 are present. Their versions are recorded. Freshness against the repo was not checked. Locale generation was tested in an ephemeral container, run as container root without `--userns keep-id`, because generation writes `/etc/locale.gen` and `/usr/lib/locale`. A realm create must run this step as root inside the container. `locale-gen` produced `en_US.utf8` offline in about a second, and the archive is 3,064,432 bytes.
- **Debian and Kali.** The `en_US` locale sources are absent. `locales` must be installed from the network before generation, which is untested.
- **Fedora.** `glibc-langpack-en` is missing. The langpack is the only Integration package to add. The `%_install_langs en_US` caveat is in section 5.
- **Fedora decision.** `fedora-minimal:44` has dnf5 5.4.6 and 106 rpm packages, against 147 for `fedora:44`. Both ship dnf5, so the dnf check does not favour the full image. The SRS asks for the minimal image, so `fedora-minimal:44` is recommended. `dnf` runs only with a writable HOME, so the realm must set HOME (the keep-id user in the probe had none, and `dnf` failed with "cannot create directories: /.local/state" until HOME=/tmp was set).
- **Package presence was confirmed by the package manager.** dpkg reported "not installed and no information is available" for `ca-certificates` and `locales` on Debian and Kali. ## 8. Open items

These do not change the verdict, which only requires a resolvable x86_64 digest per distro. They are M4 verification items.
1. Network-dependent package steps are untested: `locales` on Debian and Kali, and `glibc-langpack-en` on Fedora. Their post-install locale generation, and whether the package installs locale data under the image's `%_install_langs en_US` or Debian's `path-exclude` rules, need a host run with network access.
2. The `%_install_langs en_US` setting in the Fedora image drops langpack files for every language except en_US. A host `LANG` other than en needs that macro overridden for the Integration set (M4).
3. Fedora GPG signing: source unknown. Debian Docker Content Trust: not probed.
4. Cosign verification of the Arch bundle to the Fulcio root and Rekor inclusion (needs the TUF root).
5. Kali channel: AS-024 covers only Debian and Fedora. The SRS author decides rolling versus last-release.
6. Fedora 45 GA: `45` exists on both registries and `latest` is 44. Whether 45 is GA was not verified (not a registry). If 45 is GA, the pin is one release behind until it is refreshed.
7. Arch CA packages: `ca-certificates` 20240618-1 and `ca-certificates-mozilla` 3.131-1 are recorded. The bundle's file list and freshness against the repo were not checked (network, and no in-image file list).
8. Setting `HOME` in realms: `dnf` fails without a writable HOME under `--userns keep-id`. Realm environment setup must provide one (T2.13/M4).
