## 3. Product findings (diagnoses, not fixed here)

### T716-1: a services-on container cannot attach session grants under /run/user/<uid> (G1, G5)

- Evidence: `scratchpad/diag/out2.log`. In a services-on arch realm (systemd is PID 1) `/proc/mounts` lists a new `tmpfs /run` (uid=100000) that covers the ginn tmpfs at `/run/user/1000`. `ls -ld /run/user/1000` inside shows `drwx------ root root`. The same check on a services-off realm shows `drwx------ soubarna soubarna` (`/run/user/1000` is ginn's tmpfs, chowned to the realm user).
- Mechanism: the create-time tmpfs `--tmpfs /run/user/<uid>:mode=0700,U` (`src/ginn/runtime/mounts.py:217`, checked in `src/ginn/runtime/spec.py:211`) is hidden when systemd mounts `/run`. The attach then runs its `mkdir -p -m 0700` as the realm user (`src/ginn/runtime/attach.py:375`, `_runtime_subdir`), whose docstring says the realm user owns `/run/user/<uid>` (`attach.py:350-360`). That premise is false on services-on realms, so the mkdir fails with EACCES. It fails for `ginn exec`, `ginn enter` (through the attach in `src/ginn/cli/_enter.py`) and the rebuild's grant attach (G5).
- Scope: any session grant whose path is under `/run/user/<uid>` (the Wayland socket, the pipewire and pulse sockets, the session bus). The desktop session has them, so on this host `ginn exec` and `ginn enter` fail on every services-on realm. The G3 and G6b gates pass only with the stripped session of section 4.
- Proposed fix (not applied; the design is the orchestrator's): have the services-on create also write a tmpfiles.d drop-in `d /run/user/<uid> 0700 <uid> <uid> -` next to the existing ADR-007 mitigations, so systemd recreates the directory owned by the realm user at boot. Or perform the grant parents' mkdir as root with an fd-anchored check, which needs an ADR decision because `_runtime_subdir` avoids root writes on purpose. Either needs an amendment to ADR-003 or ADR-007, and the G1 and G5 gates re-run after it.

### T716-2: the token kill cannot read a container-root process's environ, so it reports nothing (G7)

- Evidence: `scratchpad/g7rerun.log`, `environ_probe_before_kill`. For `--root sleep 300`, `/proc/<pid>/environ` is EACCES, so `tokened()` returns 0 for it. The sweep then finds no tokened process and the kill helper returns 0 at once (`native/ginn-exec-kill.c:62-63` returns 0 on `open` failure, `:124` returns 0 when a sweep finds nothing). The lock is released at 0.05 s, the process survives for 60 s, and no orphan marker is written. The `--user sleep 301` probe is readable and the token is present: its target is gone in 0.19 s with the lock released at 0.15 s. The `env -i` case escapes by design (`env_i_escapes_token_kill=True`).
- The ADR O8 expectation (the owner of the rootless user namespace reads the environ of container-root processes) is disproved for `--root`. It holds for `--user`.
- Two product defects follow. First, an unreadable process is counted as "not tokened" and is silently ignored, so the lock is released and the orphan marker is never written. That is not fail-closed (ADR-014, Worker lifetime). Second, the `--root` token kill does not work at all.
- Proposed fix (not applied): (a) in `tokened()`, treat an unreadable environ as an unknown survivor: count it, keep sweeping to the bound, and write the orphan marker with `unreadable` pids. (b) For `--root`, identify the exec's processes another way, for example by the ppid chain from the crun exec child, or by the exec's own pidfd tree, instead of environ. (c) Until (b) exists, the ADR must say that `--root` execs are not covered by the token kill, and that an interrupted `--root` exec can leave a process running with the lock released. This needs a decision by the orchestrator.

### T716-3: a fresh services-on realm has no sync database (G4 first run, CL-18)

- Evidence: `scratchpad/g4.log`: `warning: database file for 'core' does not exist (use 'pacman -Sy')`, `GINN-E-PKG-MANAGER`. The create of a services-on realm returns at `src/ginn/ops/create.py:236-239` (`if self._plan.spec.services: return self._finish_services()`), which skips `_integrate()` (the arch refresh, `create.py:548-562`). CL-18 (`docs/clarifications.md:191-198`) records this as open: a services-on create installs nothing until its first rebuild. ADR-015 (CL-30) would change it. So this is a known deferral, not a regression. The install error gives pacman's raw text and no remedy.
- The gates that install into a fresh services-on realm run the arch refresh argv through the relay first (section 4). Nothing else was changed.
