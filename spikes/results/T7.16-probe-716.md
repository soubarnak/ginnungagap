The `--user` sleep reads. Its environ has no `GINN_EXEC_TOKEN` key because the probe started it as a
non-mutating exec, which carries no token. The `--root` sleep is the mutating exec that carries the token.

### A2: `nsenter` into the user namespace, then read

```
A2 nsenter -U -t 23681 -- cat /proc/23681/environ                      rc=0  (environ printed, GINN_EXEC_TOKEN present)
A2 nsenter --preserve-credentials -U -t 23681 -- cat ...               rc=1  cat: /proc/23681/environ: Permission denied
A2 nsenter -U -t 23689 -- cat /proc/23681/environ                      rc=0  (same content)
A2 nsenter --preserve-credentials -U -t 23689 -- cat ...               rc=1  cat: /proc/23681/environ: Permission denied
A2 nsenter -U -t 23689 -- cat /proc/self/status (Uid line)             Uid: 0 0 0 0
```

Without `--preserve-credentials`, `nsenter -U` becomes uid 0 inside the namespace, which is kuid 100000. That
matches the owner of the file, so the read works. With `--preserve-credentials` the `cat` keeps kuid 1000, and
it loses its capabilities on `exec`, so the read fails.

### A3: Yama, owner, dumpability

- `ptrace_scope` = 1. Yama restricts only `PTRACE_MODE_ATTACH`. Environ, mem and maps reads use
  `PTRACE_MODE_READ`, so Yama does not explain the denial.
- Dumpability cannot be read from the host. The `environ` owner of the `--root` sleep is kuid 100000, which is
  also the owner a non-dumpable process would show (the root of its mm's namespace). So the owner does not
  settle dumpability.
- `maps` (mode 0444) is readable from the host for the `--root` sleep. Opening `maps` runs the same
  `PTRACE_MODE_READ` mm check as `environ`, so that check passes from the host.

### A4: signals from the host user

A4 pidfd_open(23681) + pidfd_send_signal(SIGTERM): ok
A4 /proc/23681 after 4 s:                          ENOENT (sleep exited)

The setns variant of A4 was not needed, because the host path worked.

### Answers A1 to A5

- A1: `EACCES` (errno 13) for `--root` environ and mem. `--user` environ reads fine.
- A2: `nsenter` is installed. The default `nsenter -U` reads the `--root` environ, because it becomes uid 0
  inside the namespace. `--preserve-credentials` fails with `Permission denied`.
- A3: Yama is not the cause. Owner and dumpability are not decisive. Maps readable (0444) shows the ptrace
  READ check passes from the host.
- A4: signals deliver. `pidfd_send_signal(SIGTERM)` from the host user kills the `--root` sleep.
- A5: from inside the container's user namespace the `--root` environ is readable and the token is present.

### Conclusion for T716-2

The denial is a file-permission check, not a capability or ptrace check. `/proc/<pid>/environ` has mode `0400`
and owner kuid 100000. `mem` has mode `0600` with the same owner. The host user (uid 1000) is neither the owner
nor holds `CAP_DAC_OVERRIDE` in the initial namespace, so the VFS check returns `EACCES` before any ptrace check
runs. `maps` (mode `0444`) passes the VFS check and then the ptrace check, so it reads. Inside the container
namespace the process holds `CAP_DAC_OVERRIDE`, and kuid 100000 is mapped there, so the same file check passes
(A5, and the default `nsenter`). The userns-owner rule does grant the host user the ptrace and kill rights
(A4, `maps`), but not the file-permission override. The ADR O8 expectation that the owner reads container-root
environ holds for kill and ptrace, and fails for environ.

This split comes from the errno and file modes on one process: `maps` reads, `environ` and `mem` fail. The
probe did not test the kernel code path directly.

Fix candidates, not applied and not decided:

1. The kill helper enters the realm's container user namespace (setns of a single-threaded child, as in A5)
   before it reads environ. A5 proves the read works. The kill from inside the namespace is not run here.
2. Identify the exec's processes another way (the realm cgroup and a parent chain, not environ).
3. Keep the ADR's current limit: an interrupted `--root` exec can leave a process running with the lock
   released.

### B5: user runtime directory

- `systemd-logind.service` is masked and inactive. `user-runtime-dir@1000.service` and `user@1000.service` are
  both inactive (dead). `user-runtime-dir@.service` is static, not masked.
- Masking logind is not the direct cause. Nothing starts `user-runtime-dir@1000` here, and `podman exec` opens no
  PAM session. In systemd, logind starts that unit when a user session is created. This is systemd behaviour
  stated from memory. Unmasking logind alone was not tested.

### Conclusions for T716-1

- The mechanism in the earlier results file (the tmpfs is hidden when systemd mounts `/run`) is not what this
  run shows. The ginn tmpfs is visible and mounted at `/run/user/1000`, on top of the `/run` tmpfs.
- The failure is ownership. The tmpfs root is owned by container root (kuid 100000) with mode `0700`, because
  the `U` option chowned it to root. The realm user (1000) cannot create anything in it, so the attach fails
  with `EACCES`. The `U` owner is set at create. For services-on the container runs as root (systemd is PID 1).
  That is an inference from the mount options and the observed owner, not a measured fact. The earlier results
  file records the services-off realm owned by `soubarna`, and this run did not re-measure that.
- The drop-in fixes the ownership at boot (B4), and the real-session `ginn exec --root` then succeeds. This is
  tested on the arch image on one boot. The fix is not wired into the product here.
