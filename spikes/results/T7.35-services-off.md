# T7.35 services-off storage measurement (FR-121, ADR-015 Decision 11b)

- Date: 2026-10-18
- Host: `xserve`, Linux 7.2.11_1, rootless, user soubarna (uid 1000)
- Podman: 5.8.8 (flagged). Queried through the product adapter, so every call carried `--root`, `--runroot` and `--tmpdir`, with `XDG_RUNTIME_DIR=/run/ginn/1000` (owned by soubarna).
- Podman root: `/home/soubarna/.local/share/ginn/podman`. Image tmpdir: `/home/soubarna/.local/share/ginn/image-tmp`, 79,984,805 bytes before and after, the 2026-10-15 entry untouched.
- Code: worktree `adr-015`, the uncommitted T7.35 tree on base 3af2c91. Nothing staged or committed.

## Method

- One run at a time. Each run passes a gate, then one traced `ginn create <distro> --name t735-<distro>-<on|off> --services <on|off>`, then one traced `ginn delete ... --purge-home --yes`.
- Gate before every create: `ginn --json integrity` must read `unchanged` (it did on all five), `ginn --json list` must be `{"realms": []}`, and `podman images` and `podman ps -a` must be empty.
- Harness: the T7.33 `trace.py` in the scratchpad. It wraps the podman calls and runs a sampler every 1 s. Each sample is `du -x` (apparent `-sbx`, allocated `-sxB1`) of the podman root through `podman unshare`, plus `statvfs`. The helper paths point at `native/build`, because `/usr/libexec/ginn` does not exist on this host (the same patch as the T7.33 harness).
- Peak = maximum sampled allocated bytes minus the first sample (empty storage). The apparent peak is reported alongside. End = the last sample of the create trace, after the create returns.
- Required and free are taken from the create's own `space-checked` progress object on stderr (`required_bytes`, `free_bytes`).
- Headroom = (required − peak_alloc) / peak_alloc. The verdict uses the allocated peak.
- After delete = the last sample of the delete trace minus the empty baseline.
- The statvfs free drop is not used. The filesystem is shared with other activity (free space fell about 5 GB during the fedora create), so it is context only.

## Verdicts

- **fedora, services-off:** pass. Peak 427.38 MB against 493.60 MB required, 15.5% headroom.
- **kali, services-off:** pass. Peak 342.22 MB against 400.84 MB required, 17.1% headroom.
- **arch, services-off:** pass, with the thinnest raw margin. The measured peak of 907.97 MB sits 0.12% below the formula's raw peak of 909.03 MB. The 1.10 margin carries the bound, which leaves 10.1% headroom.
- **debian, services-off (fixed code):** pass. Peak 225.99 MB against 264.47 MB required, 17.0% headroom. The earlier T7.35 trace gave 225.14 MB peak against 264.5 MB, so the re-measure is within 0.9 MB.

No peak exceeded its required figure, so the series ran to completion and no stop was needed. The T7.33 services-on figure of 347.90 MB is the raw absolute maximum of allocated bytes in `t733/debian.jsonl` (`analyze.py`, not measured above the empty baseline). Measured above the baseline, the same trace gives 347.5 MB, and this re-run gives 347.49 MB. The two definitions differ by the 0.40 MB baseline, so 347.49 MB is the figure to compare with the services-off rows.

Against the raw formula (`services_off_peak_bytes`, pull counted), the measured peaks are 94% (debian), 95% (fedora), 94% (kali) and 99.9% (arch) of the modelled raw peak. Each model is an upper bound on the measured value.

## Pinned rotation: modelled, not measured

The rotation is modelled with the product's own `services_off_peak_bytes` and `services_off_required_bytes` (read-only call, no podman). A rotated pin is pulled and copied again, so the model uses `base_pulled=True`, the same term as a create that pulls. The same pin already in storage uses `base_pulled=False`.

| Distro | Rotation raw peak MB | Rotation required MB | Same-pin required MB |
|---|---|---|---|
| debian | 240.43 | 264.47 | 167.76 |
| fedora | 448.72 | 493.60 | 326.58 |
| kali | 364.40 | 400.84 | 250.99 |
| arch | 909.03 | 999.93 | 522.28 |

The rotation figure equals the create figure above, because a rotation pulls the base as a create does. This is read from the code, not run: the pinned build's check (`ops/create.py` `_check_space_for`) calls `_create_plan.storage_required`, which calls `storage_peak_for(services=False, base_pulled=not base_in_storage)`. So a rotated pin (not in storage) takes `base_pulled=True`, and the same pin in storage takes `False`. It does not count the old generation's disk use while the new base is pulled (the old base, its keep-id copy and the old container's writes, if still present). That is the FR-020 current-use term, which ADR-015 defers and which is not built. So the rotation figure is not a full bound if the old generation is still on disk when the pull runs. This is not measured, and the owner decides whether the term is needed.
