# S-08: stale session sockets bind-mounted into a container (CL-5)

Status: the real-logout attempt below is invalid. The simulated logout (the last section) gives the verdict for CL-5.

Run: 2026-10-12, Void glibc x86_64, kernel 7.2.9_1, rootless podman 5.8.8, crun 1.30.1. Script: `spikes/s04_s08_logout.sh` (`s08-*` subcommands), helpers `spikes/s04_s08_sockserver.py`, `spikes/s04_s08_probe.sh`, `spikes/s04_s08_rebind.py`. Same throwaway user and private sshd as S-04 (see `spikes/results/S-04.md`, which holds the root command list and cleanup proof).

## Verdict

S-08: invalid: no elogind session. Not run.

S-08 depends on S-04's login setup. An ssh login as `ginn-spike` did not register with elogind, so `/run/user/<uid>/s08.sock` could not be created in a login session, and the logout that tears down the runtime dir could not be tested. Nothing about CL-5 was measured.

CL-5 stays open. It is not resolved to "restart required", because the unprivileged rebind was never attempted.

## Simulated logout (S-04s/S-08s)

Same simulation as in S-04.md, section "Simulated logout (S-04s/S-08s)": it removes the runtime directory and does not kill processes. It is not a real logout, so the PAM and elogind teardown is not covered. Scripts: `spikes/s04s_s08s_sim.sh` (subcommands `start`, `logout`, `login`, `s08-probe`, `s08-rebind`), `spikes/s04s_s08s_uclient.c`, `spikes/s04s_s08s_rebind.py`, plus the S-08 helper `spikes/s04_s08_sockserver.py`. Raw logs are in the session scratchpad, outside the repository (`s04s-final/`).

### Setup

- Socket server `gen1` (python3, `s04_s08_sockserver.py`) listens at `$SIM_RUNTIME/s08.sock` (`/run/user/1000/ginn-spike-s04sim/s08.sock`).
- Container `s08c` with variant A flags (runroot `/dev/shm/ginn-spike-s04sim-ginn/podman`, tmpdir `/dev/shm/ginn-spike-s04sim-ginn/tmp`, `XDG_RUNTIME_DIR=/dev/shm/ginn-spike-s04sim-ginn`) and `-v $SOCK:/run/s08.sock -v $CLIENT:/opt/uclient:ro`.
- Probe client: `uclient`, statically linked and bind-mounted read-only. It was needed because busybox `nc` in alpine:3 has no unix-socket mode (`nc --help` lists no `-U`). It prints the inode and type of the path, connects, and prints the reply.
- Baseline from inside `s08c`: `stat: ino=16693 socket=yes`, `reply: gen1 pid=18472`.

### Logout, login, stale check

- Logout: `gen1` stopped (SIGTERM), `$SIM_RUNTIME` removed. Login: `$SIM_RUNTIME` recreated empty, `gen2` started at the same path, host inode 16749.
- `s08c` kept running. Its init pid (18561) and StartedAt did not change. Only its view of the socket is stale.
- Probe after login: `stat: ino=16693 socket=yes`, `connect: errno=111 (Connection refused)`. The container still holds the unlinked gen1 inode, and no process listens on it. This is the expected stale result.

### Rebind without restart

The attempts ran in this order, all against the same stale mount. Each was followed by a probe. Full output is in the run log.

| # | Command, user namespaces | Result |
|---|---|---|
| 1 | `podman` (variant A flags) `unshare nsenter --mount --target <pid> mount --bind $SOCK /run/s08.sock` | rc 255: `mount: mounting .../s08.sock on /run/s08.sock failed: No such file or directory`. The host path is not visible in the container's mount namespace. Probe still stale. |
| 2 | same, with `nsenter --user --mount` | rc 1: `nsenter: reassociate to namespaces failed: Invalid argument`. `podman unshare` is already in the container's user namespace (same inode as the container init), so there is nothing to join. Probe still stale. |
| 3 | `podman ... unshare python3 -I s04s_s08s_rebind.py <pid> $SOCK /run/s08.sock` (no unmount) | open_tree ok; setns user skipped (same namespace); setns mnt ok; `move_mount: FAILED errno=2 (No such file or directory)`. Probe still stale. |
| 4 | `python3 -I s04s_s08s_rebind.py <pid> $SOCK /run/s08.sock` (plain session) | `open_tree: FAILED errno=1 (Operation not permitted)`, CapEff 0. Probe still stale. |
| 5 | `podman ... unshare python3 -I s04s_s08s_rebind.py <pid> $SOCK /run/s08.sock --unmount-first` | open_tree ok; setns user skipped; setns mnt ok; `3b umount2: ok`; `4 move_mount: ok`, rc 0. Probe: `stat: ino=16749`, `reply: gen2 pid=26079`, rc 0. |
| 6 | plain session, `--unmount-first` | `open_tree: FAILED errno=1 (Operation not permitted)`. Probe unchanged (gen2). |

Observed namespace topology: the plain session user namespace is `4026531837` (the initial one). The container init's user namespace is `4026533097`, and `podman unshare` reports the same user namespace. Its mount namespace is separate. So `podman unshare` enters the rootless user namespace that holds this container, and the plain session is outside it. The container was created inside that namespace, so the causal link runs from the store's rootless namespace to the container. Whether that namespace belongs to the rootless pause process was not checked. The practical limit: ginn can rebind only into a container of a store whose rootless user namespace it can enter this way. It cannot reach an arbitrary container.

Diagnostics run in the same stale state (inline, not in the repository, copies in `s04s/`):

- `move_mount` of an `open_tree` clone of the socket, or of a regular file, onto an ordinary path in the container (`/tmp/rebind-probe-target`): rc 0 for both sources. The cross-namespace move works.
- The same two sources onto `/run/s08.sock` without unmount: ENOENT for both. The failure depends on the mount being stacked on, not on the source.
- Stacking a regular file onto a live mount (`/opt/uclient`): rc 0.
- Reading: the stale mount's root is the socket the logout unlinked. The kernel refuses to stack on that, so the ENOENT is probably `get_mountpoint` on an unlinked dentry. This is an inference. The kernel source was not checked.

S-08s: rebind feasible unprivileged, without a restart (podman unshare, umount2 of the stale bind mount, then move_mount of the fresh socket). Simulated.

Verdict S-08s (simulated): rebind feasible without a restart. It works only from `podman unshare` (the store's rootless user namespace, see above), and only after `umount2` of the stale bind mount, then `move_mount` of the fresh socket. From the plain session, `open_tree` fails with EPERM. Restart is not required in this simulation. The container's init process and StartedAt did not change.

Caveats:

- Between `umount2` and `move_mount`, the path holds the placeholder that podman created, not a socket. That window was not measured.
- Not measured: whether processes that already hold the old socket keep using it, and whether new connects reach gen2 at once (the probe ran only after the rebind completed).
- The result depends on podman's rootless user-namespace layout (podman 5.8.8, crun 1.30.1). Not checked on other versions.
- Only the case where the server dies at logout was run. A server that survives logout, with the socket unlinked under it, was not tested.
- The rebind runs as the container's owner uid (1000). A container whose user namespace has another owner was not tested.

### Run history

The first run (`s04s/`) used an earlier version of the rebind helper. It failed at step 3 for the bug described in S-04.md. Attempts 1 and 2 gave the same errors as in the final run. The diagnostics above come from that first run, on the stale mount left by the first logout.

## S-08t: rebind under keep-id

Run: 2026-10-12, same host, kernel and podman/crun versions as S-08s, as uid 1000, no root. Scripts: `spikes/s04s_s08s_sim.sh` (`GINN_S08_KEEPID=1 start`, `s08-try row5|b|row3`), `spikes/s04s_s08s_rebind.py` (new flag `--no-setns-user`). Raw logs (`run.log`, `commands.log`, `pins.txt` per cycle) are in the session scratchpad, `s08t/`, outside the repository.

### Verdict

Keep-id rebind works without a restart. Two variants reach gen2 with no failing step, and the container's init pid and StartedAt do not change: (a), which is row 5 run under keep-id, and (b), which enters only the mount namespace. A restart is not required for keep-id realms in this simulation. The restart-required alternative is not adopted.

ADR-008 is not updated here, because it is outside this task's file list. Its text needs changes (see Follow-up).

### Setup

- The base argv was `--runtime crun --userns keep-id --init --network host`, plus `-v $SOCK:/run/s08.sock -v $CLIENT:/opt/uclient:ro` and `alpine:3 sleep infinity`. Two additions. `--init-path <stand-in>` is needed because no catatonit sat on a podman search path when the runs started. `--cgroups disabled` was not added: `pa run` accepted the argv without it.
- Stand-in: `$STORE/catatonit`, copied from `~/.cache/ginn-spike/s07c/catatonit` in `build`. sha256 `32ab6262b8735f567bfc42515218905e40dc8306aa2d763ffbffeb3956a20a96`, `tini version 0.2.1_catatonit`.
- Host catatonit: the Void package (0.1.7) was installed at 14:31:42 (orchestrator note). Every pause process in these runs was `catatonit -P`, started at 14:31:44 or later. The S-08s runs used whatever pause was present then; not recorded.
- Keep-id containers ran without `s04a` and `s04b`. The control container `s08c` used the S-08s flags (`--cgroups disabled --network none`, no keep-id).

Command for variant (a), the keep-id container's rebind (XDG pinned, all three storage flags):

```
env XDG_RUNTIME_DIR=/dev/shm/ginn-spike-s04sim-ginn podman --root $HOME/.cache/ginn-spike-s04sim/a/root \
  --runroot /dev/shm/ginn-spike-s04sim-ginn/podman --tmpdir /dev/shm/ginn-spike-s04sim-ginn/tmp --runtime crun \
  unshare python3 -I spikes/s04s_s08s_rebind.py <init pid> /run/user/1000/ginn-spike-s04sim/s08.sock /run/s08.sock --unmount-first
```

Variant (b) adds `--no-setns-user`. Keep-id container create argv, as logged: `... --runtime crun run -d --name s08c --runtime crun --userns keep-id --init --init-path $STORE/catatonit --network host -v ...:/run/s08.sock -v ...:/opt/uclient:ro docker.io/library/alpine:3 sleep infinity`. `--runtime crun` appears twice because `pa` adds it and the base argv includes it.

### Procedure

Each cycle is a separate `GINN_SPIKE_OUT`: `start`, then `logout` (gen1 stopped, `$SIM_RUNTIME` removed, 15 s), then `login` (gen2 at the same path), then one `s08-try`, then `reap`. Each container is fresh, so no try sees another's change to the mount table.

Errno: the helper prints `ok` for each step that succeeds, and `FAILED errno=N` for the first one that fails. The only failure in this table is row 3's `move_mount`, errno 2 (ENOENT), which matches S-08s row 3. The umount step is still needed under keep-id.

Probe before each attempt (stale): `stat` gives the gen1 inode, `connect: errno=111 (Connection refused)`. Probe after a successful attempt: the gen2 inode and `reply: gen2 pid=...`. Pass criterion: met for (a) and (b).

Variant (a) is the helper's default path. Under keep-id, `setns user` is not skipped, so it runs before `setns mnt`. The row 5 invocation and variant (a) are the same command. The reordering with `open_tree` after `setns user` was not run, because neither (a) nor (b) failed.

### Namespace inodes

Cycle row 5 under keep-id (variant a), listed before the attempt:

```
plain session:              user=4026531837  mnt=4026531832
podman unshare:             user=4026532812  mnt=4026532816
container init (pid 28798): user=4026533089  mnt=4026533101
uid_map podman unshare:     0 1000 1; 1 100000 65536
uid_map container init:     0 100000 1000; 1000 1000 1; 1001 101000 64536
```

The keep-id container's user namespace is not the store's: its inode differs from `podman unshare`'s. Its mount namespace is separate too. `setns` into it from `podman unshare` succeeded, which the kernel allows only for a namespace under the caller's own. So it is a child of the store's namespace (inferred from the kernel rule, not checked against the source).

Other cycles, same listing format:

| Cycle | podman unshare user / mnt | container init user / mnt |
|---|---|---|
| control, non-keep-id | 4026533089 / 4026533090 | 4026533089 / 4026533282 |
| b, keep-id | 4026533167 / 4026533168 | 4026533169 / 4026533174 |
| row 3, keep-id | 4026533107 / 4026533108 | 4026533109 / 4026533114 |

In the control the container's user namespace is the store's, so the two inodes match. That is the premise S-08s relied on. Under keep-id they differ. Inode numbers are reused between cycles, so compare only within one cycle.

### Caveats

- A simulated logout, the same as S-08s, not a real one. The PAM and elogind teardown were not exercised.
- The `--init-path` stand-in differs from the installed catatonit (0.1.7), so the argv is not byte-identical to a production realm.
- `podman --version` was run once at the start with no storage flags. It opens no storage. Recorded for audit.
- Not measured: the window between `umount2` and `move_mount`, processes that already hold the old socket, and a server that survives logout. Only the server dying at logout was tested.
- Uid 1000 only, on podman 5.8.8 and crun 1.30.1.
- Pass in the simulation does not prove the real logout path.

### Follow-up (not done here)

- ADR-008 must change. Its Consequences state that "because of keep-id, that namespace is shared by the realm's container". That is wrong: the keep-id container has its own user namespace under the store's, and the helper must enter it (or skip it with `--no-setns-user`). Its decision steps list only the mount namespace, but the helper's default path enters both.
- Variant (b) enters only the mount namespace. That matches ADR-008's "enters only the container's own mount namespace" isolation statement, so the ADR may prefer it. That is a design choice for the ADR, not a finding here.
- Restart-required is not needed for keep-id realms in this simulation. The ADR should say what was tested.
