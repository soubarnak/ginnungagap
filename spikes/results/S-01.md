# S-01: systemd as PID 1 in rootless podman under a delegated cgroup (R-001)

Run: 2026-10-12, host Void Linux glibc x86_64, kernel 7.2.9_1, runit, elogind.
Script: `spikes/s01_systemd_rootless.sh`. Raw logs stayed outside the repo (per-variant `podman top`, `journalctl`, `root-steps.log`).

## Verdict

**S-01: PARTIAL**

The roadmap pass criterion (`systemctl is-system-running` is running or degraded, zero failed default units) holds with runc under a root-created, user-owned, delegated cgroup subtree (variants a and c). It is not shown for crun: crun is not installed and the spike does not install it (AGENTS.md forbids invoking xbps-*; installing needs the user's consent). Variant b cannot run as specified: podman 5.8.8 rejects `--cgroups=split` together with `--cgroup-parent`. The roadmap gate ("stop if S-01 fails on both runtimes") is not triggered, because runc passes. FR-080 AC-1, FR-080 AC-2 and FR-016 AC-2 are demonstrated on runc. NFR-003 is not decided here (see RSS).

## Environment facts

- podman 5.8.8, cgroupfs manager, rootless. runc 1.5.2 at `/usr/bin/runc` (default OCI runtime). conmon 2.2.1.
- Unified cgroup v2 at `/sys/fs/cgroup`, plus a v1 hierarchy `name=elogind` rooted at `/`.
- Root `cgroup.subtree_control` before setup: `cpuset cpu io memory`. The brief said empty; it was not. Available at root: `cpuset cpu io memory hugetlb pids rdma misc`.
- Root cgroup held 351 to 377 processes. The root cgroup is exempt from the no-internal-process rule, so enabling controllers there worked with processes present.
- The launcher shell started in `/2`, an elogind session scope owned by root. Podman cannot place containers under a cgroup that the user cannot write.
- crun 1.30.1 is packaged but not installed.
- Host memory at start: about 0.4 to 0.6 GiB MemAvailable, zram nearly full, two user qemu VMs using about 10 GB. The spike ran one container at a time and checked headroom before each step. No user container was touched.

## Recommended flag set

```
podman run -d --name <realm> --systemd=always --cgroupns private \
  --cgroup-parent /ginn/<uid>/<realm> --userns keep-id --user 0:0 \
  --network host --stop-signal SIGRTMIN+3 <image> /sbin/init
```

- Use the default cgroups mode. Do not add `--cgroups=split` together with `--cgroup-parent`.
- Start and exec the realm from a process that Host Setup placed in a leaf under `/ginn/<uid>` (see the root steps). Do not run podman from the session cgroup.
- The runc default was used. Use crun only after its own run is recorded.
- `--userns keep-id --user 0:0` was not varied; it worked as given.

## Root steps Host Setup (FR-001) must perform

All as root. Here `<uid>` is the user, `<gid>` the user's primary group, and `<leaf>` the leaf that the runit supervisor lives in.

1. Record the original `/sys/fs/cgroup/cgroup.subtree_control` for undo.
2. `echo +cpu`, `+memory`, `+pids`, `+io`, `+cpuset` into `/sys/fs/cgroup/cgroup.subtree_control`. On this host only `+pids` was new.
3. `mkdir /sys/fs/cgroup/ginn`, then the same five `+ctrl` writes into `/sys/fs/cgroup/ginn/cgroup.subtree_control`.
4. `mkdir /sys/fs/cgroup/ginn/<uid> /sys/fs/cgroup/ginn/<uid>/<leaf>`, then the same five `+ctrl` writes into `/sys/fs/cgroup/ginn/<uid>/cgroup.subtree_control`.
5. Place the supervisor process in the leaf: `echo <pid> > /sys/fs/cgroup/ginn/<uid>/<leaf>/cgroup.procs`. The leaf must be a child because `ginn/<uid>` has controllers enabled, so it cannot hold processes itself (no-internal-process rule).
6. `chown <uid>:<gid>` on `/sys/fs/cgroup/ginn/<uid>`, `.../cgroup.procs`, `.../cgroup.threads` and `.../cgroup.subtree_control`. Nothing else under the subtree is chowned, so limit files such as `memory.max` stay root-owned. Chowning the whole tree would let the user raise its own limits.

Undo, in order: remove containers, remove leaves deepest first, `rmdir /sys/fs/cgroup/ginn/<uid>`, `rmdir /sys/fs/cgroup/ginn`, then `echo -pids` into root `cgroup.subtree_control` (the spike restored the recorded original, `cpuset cpu io memory`). Note: if Host Setup keeps `+pids` at root, the ADR should say so.

The spike wrote all of these through `sudo "$0" --root-setup`. Every write and its result is in `root-steps.log`. No write failed.

## Shutdown (FR-016 AC-2)

- `podman stop -t 30` on the cron-enabled container: 0.3 s, 0.3 s, 0.5 s across runs, exit code 0, no OOM kill. Exit 0 well inside the 30 s timeout means systemd exited on its own, not by SIGKILL.
- A tty-attached diagnostic run showed the orderly sequence in `podman logs`: units stopped in dependency order, `Reached target final.target`, `Exiting container.`.
- Shutdown also logged `[FAILED] Failed unmounting` for the runtime's bind mounts (`/etc/hosts`, `/etc/hostname`, `/etc/resolv.conf`, `/run/.containerenv`, `/tmp`). These lines do not change the exit code. Watch for them in S-05.

## cron and restart (FR-080 AC-1, AC-2)

- `apt-get update && apt-get install -y cron && systemctl enable --now cron`: `cron` active, `is-enabled` enabled.
- `podman restart s01a`: boot settled in 0.6 s. `systemctl is-active cron` active and `is-enabled` enabled after restart.

## Disclosures

- Two read-only `xbps-query` calls were run during orientation to check the crun package version. No `xbps-install` was run.
- Root steps used sudo for cgroup writes only. The script never touches `/etc/subuid`.
- Teardown restored root `subtree_control` to `cpuset cpu io memory` and removed `/sys/fs/cgroup/ginn`.
- Teardown removed only `~/.local/share/ginn-spike/podman` and `/run/user/1000/ginn-spike`. The empty `~/.local/share/ginn-spike` parent was removed by hand. Podman's storage keeps a self-bind mount of its overlay directory inside its own mount namespace, so removal needed `podman unshare rm -rf` plus a plain rm from the host namespace. `podman system reset` was not used.
- A second spike's storage (`~/.local/share/ginn-spike-s02`) and its conmon were running on this host during the spike. They were not touched.
- The user's containers `bb-pg`, `priceless_ramanujan` and `outreach-test-pg` were not touched.
