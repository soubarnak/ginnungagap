# ADR-013: Host Setup Record, pre-images and resume

- Status: Proposed
- Date: 2026-10-12

## Context

FR-001 requires Host Setup to record every host path it writes. FR-002 requires a second run to change no host file, byte for byte, and to report "already configured". FR-003 requires undo to restore each recorded path to its pre-setup content or remove it. DR-009 defines the record: the user, the subordinate ID range, every host path written and the timestamp. NFR-030 requires that after a SIGKILL at any point no data is lost and the next command finds a known state.

Undo can restore only what was captured before the first write. A record written after the first write would hold the post-crash state as its pre-image. A resume that captured pre-images again would make the same mistake.

Two groups of paths change. Setup writes files under /etc and /run/lock once, during the run. On Void it also creates the service link in the runsvdir directory that `/var/service` resolves to (Decision 10). The supervisor run script writes the root `cgroup.subtree_control` and the `ginn` cgroup directories each time the service starts (ADR-003, spike S-01). Setup does not run that script, so it cannot record those writes as they happen. It must capture their pre-images before the service can start.

Ranked characteristics (SRS section 4): recoverability and host integrity settle the decision. A rerun must never change a host file (host integrity), and an interrupted run must be recoverable with the true pre-setup state (recoverability). Performance does not apply, because Host Setup runs once.

## Decision

1. Persist before write. Setup captures the pre-image of every path it will write, and of each service-written path, and then writes the records with status `pending`. The record writes are the first writes to the host, with one exception. When `etc/ginn` does not exist, `shared.json` and the per-user record are written into the temporary directory of Decision 16, and that directory is renamed into place only after both are in it.
2. Resume keeps the stored pre-images. A pending record is never captured again. A repair stores the new uid, gid and timestamp, keeps every pre-image, sets status `pending` before the next write, and writes the new post-images when it completes. The same holds for `shared.json` (Decision 17).
3. Lists. `paths` holds the per-user paths that setup writes, each with a pre-image and, once complete, a post-image. `service_paths` holds the per-user paths that the run script writes at service start, with pre-images only. Shared paths, from either list, are held only in `shared.json` (Decision 17), so each path has exactly one holder. Undo treats the two per-user lists differently: a service path may not exist when undo runs.
4. Idempotence (FR-002). The check reads only the records, the per-user record and `shared.json`, and it takes no lock. A complete per-user record whose setup-written paths still match their post-images (digest and mode), whose subordinate ID entries cover the recorded ranges (Decision 16), and with `shared.json` present, means "already configured". The run then creates no file, takes no lock and writes nothing, not even the record. The record's mtime, the directory mtimes and `/run/lock` stay the same. Any other state goes to the repair path, which takes the lock (Decision 11).
5. `/etc/subuid` and `/etc/subgid` are listed with pre-images like every other file, with kind `append-lines` (Decision 13). The idempotence check compares their entries for the user, not their digests, because another user's setup appends lines to them.
6. Subordinate IDs. A first run records one range per file: the user's own line if it already holds at least 524,288 IDs, otherwise a new full-size line placed by `allocate`. The record is rewritten, still pending, once both ranges are known. A repair reuses the recorded ranges (`ensure_exact`). If another line overlaps a recorded range, setup raises GINN-E-SUBID-CONFLICT and changes nothing. It never chooses another range.
7. Placement. Every host path is placed under `root_dir`, including the records, the lock directory, the lock file and the link. The contents of the rendered scripts and the link target keep their host paths, such as `/run/ginn/<uid>` and `/etc/sv/ginn-<user>`. Setup does not require `/run/ginn/<uid>` (ADR-004).
8. Cgroup delegation. Setup does not call `cgroups.delegate_user_tree`. The run script does the same writes when the service starts (ADR-003, `runit_system.py` step 2), and those paths are recorded as service-written (Decisions 3 and 12).
9. Each record lists its own file with pre-image `absent` and post-image `self`, because its digest cannot be stored in itself. This holds for the per-user record and for `shared.json`.
10. Void service directory. On Void, `/var/service` is a symlink chain: `/var/service` -> `../run/runit/runsvdir/current` -> `/etc/runit/runsvdir/current` -> `default`. This was checked read-only on the reference host on 2026-10-12. Setup follows symlinks at any component that it reaches while it resolves the `var/service` chain. It resolves the chain inside the root: absolute targets are re-rooted under `root_dir`, and a `..` cannot leave the root. The chain must end at a root-owned directory inside the root. If it does not, setup refuses with GINN-E-SETUP-PATH-UNSAFE before its first write. The service link is created and recorded at the resolved path, `/etc/runit/runsvdir/default/ginn-<user>`, with pre-image `absent`. `var` itself and every other path refuse symlinks, with the same error.
11. Global lock. Setup and undo take `/run/lock/ginn-host-setup.lock` (under `root_dir` in tests). A run first does the lock-free check of Decision 4. If the record does not say "already configured", the run takes the lock, loads the records again and repeats the check under the lock, before its first write. If the check under the lock says "already configured", the run touches nothing. The lock is global, not per user, because `etc/ginn`, `sys/fs/cgroup/ginn` and the root `cgroup.subtree_control` are shared by all users. A run that cannot take the lock polls for 30 s, then stops with GINN-E-SETUP-BUSY (exit 75). That code is ginn-defined, not an SRS code, and `docs/errors.md` lists it. The lock file is not recorded, and undo does not remove it. It is an empty file in tmpfs, which a reboot clears. Removing it could let two runs lock different inodes.
12. Shared and per-user classification (D9). This replaces the list of shared paths in the earlier Decision 12. A path is per-user when one of its components is the decimal uid, the name `ginn-<user>`, or the name `setup-<user>.json`. Every other path is shared. At present the shared paths are `/etc/ginn`, `/etc/sv`, `/run`, `/run/ginn`, `/sys/fs/cgroup/ginn`, the root `/sys/fs/cgroup/cgroup.subtree_control`, and any shared ancestor that setup creates. The per-user paths are `/etc/sv/ginn-<user>` with its files, the service link `/etc/runit/runsvdir/default/ginn-<user>`, `/sys/fs/cgroup/ginn/<uid>`, `/sys/fs/cgroup/ginn/<uid>/supervisor` and `/run/ginn/<uid>`. The rule applies to the setup-written and the service-written paths alike. Two kinds of entry are per-user whatever their path. The two `append-lines` subid entries are per-user, because `/etc/subuid` and `/etc/subgid` are shared files but each line that setup appends belongs to one user. The record itself is per-user. Each record has one top-level `boot_id` (`/proc/sys/kernel/random/boot_id`), read when the record's first pre-image is captured, and kept by a repair (Decision 2). Undo's boot test (Decision 15 (ii)) reads the `boot_id` of `shared.json`.
13. Record schema 3 (D9). Schema 1 is the form committed in 63de96e. Schema 2 is the form committed in F8a (94cb2ae). It added `shared`, put `boot_id` on the service-written entries, gave each post-image a `mode` as well as its `sha256`, and used kind `append-lines` for the two subid files. Schema 3 keeps those fields. It moves `boot_id` to the top level of each record (Decision 12), and adds a top-level `kind` marker that tells the per-user record and `shared.json` apart. Each entry keeps its `shared` field, set by the rule of Decision 12. A schema 1 or schema 2 record is refused with "written by a build before F8a/F9a". The record files are mode 0600, because they hold the pre-image content of host files.
14. Doctor reads host state. `doctor/checks.py` (T3.6) reads the subordinate ID lines, the `/etc/sv/ginn-<user>` directory, the service link and the cgroup tree. It never reads the Host Setup Record. Its root controller tolerance comes from the current root `cgroup.subtree_control`, not from the record. Its subordinate ID check applies the one-line rule of Decision 16.
15. Undo rules (D9). These rules bind T3.5 (`hostsetup/undo.py`). Undo dispatches on each entry's `kind` and `shared`, and on the top-level `kind` of each file. It never dispatches on path lists. Undo takes the global lock of Decision 11 for the whole run. It also works from a `pending` record, and then it uses the pre-images alone. Every removal tolerates ENOENT, and every restore skips a path that already matches its pre-image. A re-run after an interrupt therefore completes without error. The realms-exist check (GINN-E-UNDO-REALMS-EXIST, FR-003 AC-2) is unchanged. It runs first and changes nothing.
    - (i) Subordinate ID lines. For each `append-lines` entry, undo removes the recorded `name:start:count` line through `subids.remove_exact`, and only when two conditions hold. The line matches the recorded range exactly. The line is absent from the stored pre-image, so a line that the user already held when setup first ran (Decision 6) is kept. A same-name line that differs, through an admin edit or a widening, stays in place, and undo prints a warning. Undo never restores `/etc/subuid` or `/etc/subgid` as whole files, and never writes pre-image bytes back.
    - (ii) Root `cgroup.subtree_control`. Undo applies this from `shared.json`, and only when the record being undone is the last one, pending or complete. It runs after the cgroup leaves and directories are removed (step 3 of (v)). It runs only when the `boot_id` of `shared.json` matches the current boot, because cgroup state does not survive a reboot. It writes `-<ctrl>` for each controller that the pre-image does not list. It never writes the pre-image bytes back, because cgroupfs does not accept them. cgroup v2 does not disable a controller that a child cgroup still uses, which is why this step follows the removal.
    - (iii) Shared directories. Undo applies this from `shared.json`, and only when the record being undone is the last one. Each shared directory whose pre-image is `absent` is removed with `rmdir`. ENOTEMPTY is not an error: the directory stays, because another user's entries are in it, and undo reports it. The directory that holds the records is not in this step. Step 6 of (v) removes it.
    - (iv) Nothing marked shared is restored by writing bytes back. Undo reverses the change that setup made.
    - (v) Order. For the record being undone, undo runs these steps in this order.
        1. Remove the service link. A link whose pre-image is absent is removed. A link whose pre-image was a symlink has its target restored.
        2. Wait for runsv to exit. The wait is injectable and has a timeout, which T3.5 sets.
        3. Per-user cleanup. Remove the per-user service paths, leaf first: `ginn/<uid>/supervisor`, then `ginn/<uid>`. Each is removed with `rmdir`, and only when its pre-image is absent. Remove `/run/ginn/<uid>` recursively only when its pre-image is absent. It sits in tmpfs, and no realm exists there when undo runs (FR-003 AC-1 and AC-2). Remove the subordinate ID lines (i), and restore or remove the per-user files and directories (vi).
        4. If the record is the last one, apply (ii), then apply (iii) to the shared directories, except the directory that holds the records, and then remove `shared.json`. If `shared.json` is already absent when the last record is undone, an earlier undo applied these steps and was interrupted. Undo skips them and prints that it did.
        5. Remove the own record. It is the last pre-image holder that undo removes.
        6. If the record was the last one, `rmdir` the directory that holds the records, `/etc/ginn`. Its pre-image is absent. The directory cannot be removed while the record is in it, so this step follows step 5. ENOTEMPTY is reported, not an error.
    - (vi) Per-user files and directories. The `/etc/sv/ginn-<user>` directory and its scripts (`run`, `finish`, `log/run`) are restored from their pre-images, or removed when the pre-image is absent, as FR-003 AC-1 requires. Writing pre-image bytes back is allowed here, because these paths are per-user. Rule (iv) covers shared paths only.
    - Printing. Undo prints every path that it leaves in place, with the reason, for example "pre-image present", "shared, used by another record" or "ENOTEMPTY". The T3.5 test asserts that list.
16. Write rules (F8a, extended by D9).
    - The first creation of `etc/ginn` goes through a temporary directory. Setup creates `etc/.ginn.ginn-tmp`, writes `shared.json` and the pending per-user record into it, and renames it to `etc/ginn`. A crash before the rename leaves only the temporary directory, and it holds no record.
    - Setup writes use fixed temporary names, `.<name>.ginn-tmp`, in the target directory. A run removes any stale ones under the lock (Decision 11) before its first write.
    - Post-images carry the mode as well as the digest (Decision 13).
    - Every parent directory that setup writes into must be owned by uid 0 and must not be group- or other-writable. Setup checks each such parent before its first write, and refuses with GINN-E-SETUP-PATH-UNSAFE if one fails the check.
    - `ensure_exact` accepts a same-name line that covers the recorded range. A line covers the range when its start is at or below the recorded start and its end is at or above the recorded end. Setup then appends nothing.
    - `ensure_single` uses the one-line rule. FR-001 AC-1 needs one range of at least 524,288 IDs in each file, so two half-size lines do not count together, and setup adds a third, full-size line. T3.6 doctor uses the same rule.
17. Shared record (D9). One record, `/etc/ginn/shared.json`, serves every user. It is mode 0600, it is schema 3, and it has a top-level `kind` marker.
    - The first setup writes it inside the temporary directory of Decision 16, in the same rename that creates `/etc/ginn`. It exists exactly when `/etc/ginn` does, except in the window after an interrupted undo, which the Residuals describe.
    - It holds every shared entry: the shared directories of Decision 12, with their pre-images, and the root `cgroup.subtree_control` pre-image. It holds no subordinate ID entry. It has its own top-level `boot_id` (Decision 12). It lists itself with pre-image `absent` and post-image `self`, as Decision 9 does for the per-user record.
    - A later user's setup leaves `shared.json` alone, except that it adds a shared directory that it had to create. The entry carries that directory's true pre-image, and the entry is added only when the path is not yet in `shared.json`.
    - If `shared.json` is missing while a per-user record exists, setup refuses with GINN-E-SETUP-PATH-UNSAFE and does not recreate it. The refusal happens before the first write.
    - The reason for this record is an order problem. The earlier framing kept the shared pre-images in the first user's record only. Per-user records lost the shared pre-images when users were undone in a different order than they were set up (eighth review MJ1). This record holds them once, for all users.

## Alternatives considered

- Write the record after the writes. Rejected: a crash between a write and the record leaves a host change with no record of it.
- Capture pre-images again on resume. Rejected: the crashed run's content would become the pre-image, and undo would restore the wrong state.
- Compare digests of `/etc/subuid` and `/etc/subgid` as well. Rejected: a second user's setup changes those files, so the first user's rerun would report drift and rewrite its record.
- Pick a new range when the recorded one is taken. Rejected by the task design. The range belongs to the user's record, and a silent new range would leave the old one allocated to nobody.
- Call `delegate_user_tree` from setup. Rejected for T3.4, as Decision 8 explains. Undo for those paths is set by Decision 15.
- Lock the whole setup run per user. Rejected: the shared paths are not per user. Not added in T3.4. F8a adds one global lock (Decision 11).
- Create the lock file on the already-configured path. Rejected: a new file in `/run/lock` would break FR-002 AC-1, which requires no host change on a rerun.
- Restore `/etc/subuid` and `/etc/subgid` as whole files. Rejected: a later user's line would be lost.
- Write the pre-image bytes back to root `cgroup.subtree_control`. Rejected: cgroupfs does not accept them (Decision 15, ii).
- Follow symlinks wherever they occur. Rejected: setup follows only the Void chain at `var/service` (Decision 10).
- Keep the shared pre-images in the first user's record only. Rejected: an undo of users in a different order than their setup discards them (eighth review MJ1). Decision 17 holds them in one shared record.

## Consequences

- T3.5 undo follows Decision 15. It must not restore the pre-image of `cgroup.subtree_control` by writing bytes, and it must not assume the original value (ADR-003). ADR-003 now defers to Decision 15, by its amendment of 2026-10-12 (D9).
- Undo must remove the created files and directories listed in `paths` and in `shared.json`, within the limits of Decision 15, and treat each `service_paths` entry as possibly absent.
- Undo must not restore the pre-image of `/etc/subuid` or `/etc/subgid`. A later user's line would be lost. Undo removes that user's own exact lines from those files instead (Decision 15, i).
- FR-003 AC-1 ("restored to its pre-setup content or removed") is met for the subid files and the shared paths by reversing setup's change, not by writing bytes back (Decision 15, i and iv). That is a reading of the SRS wording, not the wording itself, and CL-11 records the gap. Removing the line setup appended, and disabling the controllers that the run script added, return each path to its pre-setup state, except where CL-11 says undo leaves a path in place. No bytes are written back, because other users' lines and live cgroup state may have changed since setup.
- The per-user record can be complete only with subordinate ID ranges and a post-image for every per-user setup path. `hostsetup/record.py` refuses to write any other record, and refuses to read a record that breaks these rules. It applies the same refusal to `shared.json` (Decision 17).
- A record that exists but cannot be read is refused with GINN-E-SETUP-PATH-UNSAFE (exit 77). That applies to `shared.json` too. It is never treated as absent, because that would capture pre-images from a host that setup already changed.
- The install split of `runit_system.py` (`install`, `install_scripts`, `install_link`) is removed by F9b. Setup writes the output of `render()` itself, under Decisions 1 and 16.
- The service-written paths are the six of Decision 12. Three are per-user (`ginn/<uid>`, `ginn/<uid>/supervisor`, `/run/ginn/<uid>`) and sit in the per-user record. Three are shared (`/sys/fs/cgroup/ginn`, `/run/ginn`, and the root `cgroup.subtree_control`) and sit in `shared.json`. T3.5 covers all six.
- Doctor reads host state, not the record (Decision 14), so a damaged record cannot hide a host fault from `ginn doctor`.

## Residuals

- Crash in the record's directory window. Closed by Decision 16. A crash before the rename leaves the temporary directory, with no record and no other write. The next run removes it under the lock.
- Controllers enabled after the pre-image. Undo (ii) cannot tell a controller that the run script added from one that another party enabled after the pre-image, within the same boot. The record keeps no post-image for that path. Undo accepts this limit.
- Reclaim gate. A stale subordinate ID lock is reclaimed through `/run/lock/ginn-<file>.lock.reclaim`, which is written only in that case and then stays. It is not recorded. It is an empty file in a tmpfs that a reboot clears.
- Concurrency. Closed for setup and undo by Decision 11. The subordinate ID lock still covers only the append.
- Lock file. `/run/lock/ginn-host-setup.lock` stays after a run, as an empty file in tmpfs (Decision 11).
- Interrupted undo, window (a). Undo removes `shared.json` (step 4 of Decision 15 (v)) before it removes the last per-user record (step 5). An interrupt between the two leaves a per-user record without `shared.json`. The next undo finishes the work, and it skips the shared steps, because they were applied before `shared.json` was removed. Setup refuses in this state (Decision 17) and names undo as the way out.
- Interrupted undo, window (b). Undo removes the last per-user record (step 5) before it removes `/etc/ginn` (step 6). An interrupt between the two leaves an empty `/etc/ginn` with no record and no `shared.json`. The next setup treats the present directory as a shared directory with pre-image present, and it writes `shared.json` into it. Undo leaves that directory and reports it. This is the one case in which `shared.json` does not exist exactly when `/etc/ginn` does.
- Racer and `/run/lock`. A run that loses the lock and then finds "already configured" may have created `/run/lock`, and no record names it. Void always has `/run/lock` on tmpfs, so the case should not arise there. Undo does not remove it.

## Requirement IDs

| ID | How this ADR bears on it |
|---|---|
| DR-009 | Defines the per-user record's contents: the user, ids, subordinate ranges, timestamp, status, and each path with its pre-image and post-image. Schema 3 adds the top-level `kind` and `boot_id`, and the shared record `shared.json`, which serves every user (Decisions 13 and 17). DR-009 does not describe a shared record. |
| DR-010 | The shared paths of Decision 12 lie outside the Owned Paths. Setup and undo write them only under Decisions 11, 15 and 17. |
| FR-001 | Setup captures pre-images, persists the records before the first write, and records each path it writes. Decisions 10, 11 and 17 add the Void chain, the global lock and the shared record. |
| FR-002 | A complete per-user record whose paths still match, with `shared.json` present, means "already configured", and nothing is written, not even the lock file (Decision 4). |
| FR-003 | Undo follows Decision 15. It depends on the stored pre-images, the classification of Decision 12, and the subordinate ID rule in Decision 16. The AC-1 wording does not hold for every path, which CL-11 records. |
| FR-007 | Doctor reads host state, not the record (Decision 14). Its subordinate ID check uses the one-line rule (Decision 16). |
| NFR-030 | A crash after any step leaves a pending record, or a temporary directory with no record, or one of the two undo windows in Residuals. The next run resumes from the stored pre-images, or removes the temporary entries under the lock. |
| NFR-040 | The refusals carry catalogue codes: GINN-E-SETUP-ROOT, GINN-E-NO-SUCH-USER, GINN-E-SUBID-CONFLICT and GINN-E-SETUP-PATH-UNSAFE. GINN-E-SETUP-BUSY (exit 75) is ginn-defined, not an SRS code, and `docs/errors.md` lists it. |
