## Context

FR-001 requires Host Setup to record every host path it writes. FR-002 requires a second run to change no host file, byte for byte, and to report "already configured". FR-003 requires undo to restore each recorded path to its pre-setup content or remove it. DR-009 defines the record: the user, the subordinate ID range, every host path written and the timestamp. NFR-030 requires that after a SIGKILL at any point no data is lost and the next command finds a known state.

Undo can restore only what was captured before the first write. A record written after the first write would hold the post-crash state as its pre-image. A resume that captured pre-images again would make the same mistake.

Two groups of paths change. Setup writes files under /etc and /run/lock once, during the run. On Void it also creates the service link in the runsvdir directory that `/var/service` resolves to (Decision 10), and it writes the two supervise links (Decision 21). The supervisor run script writes the root `cgroup.subtree_control` and the `ginn` cgroup directories each time the service starts (ADR-003, spike S-01). Setup does not run that script, so it cannot record those writes as they happen. It must capture their pre-images before the service can start.

Ranked characteristics (SRS section 4): recoverability and host integrity settle the decision. A rerun must never change a host file (host integrity), and an interrupted run must be recoverable with the true pre-setup state (recoverability). Performance does not apply, because Host Setup runs once.

## Decision

1. Persist before write. Setup captures the pre-image of every path it will write, and of each service-written path, and then writes the records with status `pending`. The record writes are the first writes to the host, with one exception. When `etc/ginn` does not exist, `shared.json` and the per-user record are written into the temporary directory of Decision 16, and that directory is renamed into place only after both are in it.
2. Resume keeps the stored pre-images. A pending record is never captured again. A repair stores the new uid, gid and timestamp, keeps every pre-image, sets status `pending` before the next write, and writes the new post-images when it completes. The same holds for `shared.json` (Decision 17).
3. Lists. `paths` holds the per-user paths that setup writes, each with a pre-image and, once complete, a post-image. `service_paths` holds the per-user paths that the run script writes at service start, or that runit creates when the service starts (Decision 21), with pre-images only. Shared paths, from either list, are held only in `shared.json` (Decision 17), so each path has exactly one holder. Undo treats the two per-user lists differently: a service path may not exist when undo runs.
4. Idempotence (FR-002). The check reads only the records, the per-user record and `shared.json`, and it takes no lock. A complete per-user record whose setup-written paths still match their post-images (digest and mode), whose subordinate ID entries cover the recorded ranges (Decision 16), and with `shared.json` present, means "already configured". The run then creates no file, takes no lock and writes nothing, not even the record. The record's mtime, the directory mtimes and `/run/lock` stay the same. Any other state goes to the repair path, which takes the lock (Decision 11). Shared directories are not part of this check, so a rerun does not see their modes (Decision 18).
5. `/etc/subuid` and `/etc/subgid` are listed with pre-images like every other file, with kind `append-lines` (Decision 13). The idempotence check compares their entries for the user, not their digests, because another user's setup appends lines to them.
6. Subordinate IDs. A first run records one range per file: the user's own line if it already holds at least 524,288 IDs, otherwise a new full-size line placed by `allocate`. The record is rewritten, still pending, once both ranges are known. A repair reuses the recorded ranges (`ensure_exact`). If another line overlaps a recorded range, setup raises GINN-E-SUBID-CONFLICT and changes nothing. It never chooses another range.
7. Placement. Every host path is placed under `root_dir`, including the records, the lock directory, the lock file and the link. The contents of the rendered scripts and the link target keep their host paths, such as `/run/ginn/<uid>` and `/etc/sv/ginn-<user>`. Setup does not require `/run/ginn/<uid>` (ADR-004).
8. Cgroup delegation. Setup does not call `cgroups.delegate_user_tree`. The run script does the same writes when the service starts (ADR-003, `runit_system.py` step 2), and those paths are recorded as service-written (Decisions 3 and 12).
9. Each record lists its own file with pre-image `absent` and post-image `self`, because its digest cannot be stored in itself. This holds for the per-user record and for `shared.json`.
10. Void service directory. On Void, `/var/service` is a symlink chain: `/var/service` -> `../run/runit/runsvdir/current` -> `/etc/runit/runsvdir/current` -> `default`. This was checked read-only on the reference host on 2026-10-12. Setup follows symlinks at any component that it reaches while it resolves the `var/service` chain. It resolves the chain inside the root: absolute targets are re-rooted under `root_dir`, and a `..` cannot leave the root. The chain must end at a root-owned directory inside the root. If it does not, setup refuses with GINN-E-SETUP-PATH-UNSAFE before its first write. The service link is created and recorded at the resolved path, `/etc/runit/runsvdir/default/ginn-<user>`, with pre-image `absent`. `var` itself and every other path refuse symlinks, with the same error.
11. Global lock. Setup and undo take `/run/lock/ginn-host-setup.lock` (under `root_dir` in tests). A run first does the lock-free check of Decision 4. If the record does not say "already configured", the run takes the lock, loads the records again and repeats the check under the lock, before its first write. If the check under the lock says "already configured", the run touches nothing. The lock is global, not per user, because `etc/ginn`, `sys/fs/cgroup/ginn` and the root `cgroup.subtree_control` are shared by all users. A run that cannot take the lock polls for 30 s, then stops with GINN-E-SETUP-BUSY (exit 75). That code is ginn-defined, not an SRS code, and `docs/errors.md` lists it. The lock file is not recorded, and undo does not remove it. It is an empty file in tmpfs, which a reboot clears. Removing it could let two runs lock different inodes.
12. Shared and per-user classification (D9). This replaces the list of shared paths in the earlier Decision 12. A path is per-user when one of its components is the decimal uid, the name `ginn-<user>`, or the name `setup-<user>.json`, or when one of its components ends in `.ginn-<user>` or `.ginn-<user>-log` (F11, Decision 21). Every other path is shared. At present the shared paths are `/etc/ginn`, `/etc/sv`, `/run`, `/run/ginn`, `/sys/fs/cgroup/ginn`, the root `/sys/fs/cgroup/cgroup.subtree_control`, and any shared ancestor that setup creates. The per-user paths are `/etc/sv/ginn-<user>` with its files, the service link `/etc/runit/runsvdir/default/ginn-<user>`, `/sys/fs/cgroup/ginn/<uid>`, `/sys/fs/cgroup/ginn/<uid>/supervisor` and `/run/ginn/<uid>`. F11 adds the two runit directories, `/run/runit/supervise.ginn-<user>` and `/run/runit/supervise.ginn-<user>-log`, which the supervise links point at (Decision 21). The rule applies to the setup-written and the service-written paths alike. Two kinds of entry are per-user whatever their path. The two `append-lines` subid entries are per-user, because `/etc/subuid` and `/etc/subgid` are shared files but each line that setup appends belongs to one user. The record itself is per-user. Each record has one top-level `boot_id` (`/proc/sys/kernel/random/boot_id`), read when the record's first pre-image is captured, and kept by a repair (Decision 2). Undo's boot test (Decision 15 (ii)) reads the `boot_id` of `shared.json`. F10 implements the rule as whole-component equality. A component matches the decimal uid, `ginn-<user>` or `setup-<user>.json` exactly, never as a substring. F11 adds the suffix form for the runit directories, which is the only exception to the whole-component rule: a name that ends in `.ginn-<user>` or `.ginn-<user>-log` is per-user. `/run/runit` matches neither form, so it stays shared, and it is not recorded. So a user named `ginn` leaves `/etc/ginn` and `/sys/fs/cgroup/ginn` shared, a user named `sv` leaves `/etc/sv` shared, and a user named `run` leaves `/run` and `/run/ginn` shared. The two subordinate ID entries are shared by path, so their `shared` field is true, and the per-user record keeps them by kind (`append-lines`) and by path.
13. Record schema 4 (D9 introduced schema 3; F11 makes it schema 4). Schema 1 is the form committed in 63de96e. Schema 2 is the form committed in F8a (94cb2ae). It added `shared`, put `boot_id` on the service-written entries, gave each post-image a `mode` as well as its `sha256`, and used kind `append-lines` for the two subid files. Schema 3 keeps those fields. It moves `boot_id` to the top level of each record (Decision 12), and adds a top-level `kind` marker that tells the per-user record and `shared.json` apart. Each entry keeps its `shared` field, set by the rule of Decision 12. A schema 1 or schema 2 record is refused with "written by a build before F8a/F9a". Schema 4 (F11) adds `home` to the per-user record (Decision 24) and the subordinate ID originals to `shared.json` (Decision 23). A schema 3 record is refused with "written by a build before F11". The record files are mode 0600, because they hold the pre-image content of host files.
14. Doctor reads host state. `doctor/checks.py` (T3.6) reads the subordinate ID lines, the `/etc/sv/ginn-<user>` directory, the service link and the cgroup tree. It never reads the Host Setup Record. Its root controller tolerance comes from the current root `cgroup.subtree_control`, not from the record. Its subordinate ID check applies the one-line rule of Decision 16. F11 adds to its reads `/run/runit` and the two supervise links (Decision 21), and it checks that `/run/runit` exists and that both links point into it. It checks the modes of the shared directories (Decision 18). A user-owned `ginn/<uid>/supervisor` leaf gets a root chown as its printed fix, because ADR-003 keeps that leaf root-owned.
15. Undo rules (D9, changed by D10). These rules bind T3.5 (`hostsetup/undo.py`). Undo dispatches on each entry's `kind` and `shared`, and on the top-level `kind` of each file. It never dispatches on path lists. Undo takes the global lock of Decision 11 for the whole run. It also works from a `pending` record, and then it uses the pre-images alone. Every removal tolerates ENOENT, and every restore skips a path that already matches its pre-image. A re-run after an interrupt therefore completes without error. The realms-exist check (GINN-E-UNDO-REALMS-EXIST, FR-003 AC-2) is unchanged. It runs first and changes nothing. "Last" means that no other per-user record file is in `/etc/ginn`. That test does not depend on whether the other user's account still exists (Decision 24).
    - (i) Subordinate ID lines. For each `append-lines` entry, undo removes the recorded `name:start:count` line through `subids.remove_exact`, and only when two conditions hold. The line matches the recorded range exactly. The line is absent from the stored pre-image, so a line that the user already held when setup first ran (Decision 6) is kept. A same-name line that differs, through an admin edit or a widening, stays in place, and undo prints a warning. Undo never restores `/etc/subuid` or `/etc/subgid` as whole files, and never writes pre-image bytes back.
    - (ii) Root `cgroup.subtree_control`. Undo applies this from `shared.json`, and only when the record being undone is the last one, pending or complete. It runs after the shared directories are removed by (iii), which is step 4 of (v). It runs only when the `boot_id` of `shared.json` matches the current boot, because cgroup state does not survive a reboot. It writes `-<ctrl>` for each controller that the pre-image does not list. It never writes the pre-image bytes back, because cgroupfs does not accept them. cgroup v2 does not disable a controller that a child cgroup still uses, which is why (iii) comes first.
    - (iii) Shared directories. Undo applies this from `shared.json`, and only when the record being undone is the last one. Each shared directory whose pre-image is `absent` is removed with `rmdir`. ENOTEMPTY is not an error: the directory stays, because another user's entries are in it, and undo reports it. The directory that holds the records is not in this step. Step 5 of (v) removes it. This step runs before (ii).
    - (iv) Nothing marked shared is restored by writing bytes back. Undo reverses the change that setup made.
    - (v) Order. For the record being undone, undo runs these steps in this order.
        1. Remove the service link. Only the service link is undone here. A link whose pre-image is absent is removed. A link whose pre-image was a symlink has its target restored.
        2. Wait for runsv to exit. The wait is injectable and has a timeout, which T3.5 sets. The waiter opens `supervise/ok` through the supervise links (Decision 21), so those links stay in place until the wait confirms exit. On timeout, undo stops before step 3 with GINN-E-UNDO-SERVICE-RUNNING (Decision 26).
        3. Per-user cleanup. Remove the supervise links and the two `/run/runit/supervise.ginn-<user>{,-log}` directories, as Decision 22 says. Remove the per-user service paths, leaf first: `ginn/<uid>/supervisor`, then `ginn/<uid>`. Each is removed with `rmdir`, and only when its pre-image is absent. Remove `/run/ginn/<uid>` recursively only when its pre-image is absent. It sits in tmpfs, and no realm exists there when undo runs (FR-003 AC-1 and AC-2). Remove the subordinate ID lines (i), and restore or remove the other per-user files, directories and symlinks (vi).
        4. If the record is the last one, apply (iii) to the shared directories, and then apply (ii) to root `cgroup.subtree_control`. The order matters, because cgroup v2 refuses `-<ctrl>` while a child cgroup still uses the controller. Then settle the subordinate ID files (Decision 23). If `shared.json` is already absent when the last record is undone, an earlier undo applied these steps and was interrupted. Undo skips them and prints that it did.
        5. Remove the records. For a record that is not the last one, remove the own record. For the last one, Decision 25 applies. The directory `/etc/ginn` leaves in one rename, and the temporary directory is then emptied, `shared.json` first and the own record last, and removed. Where the conditions of Decision 25 fail, undo removes `shared.json`, then the own record, and leaves `/etc/ginn` in place and reports it. The own record is always the last pre-image holder that undo removes.
    - (vi) Per-user files and directories. The `/etc/sv/ginn-<user>` directory and its scripts (`run`, `finish`, `log/run`) are restored from their pre-images, or removed when the pre-image is absent, as FR-003 AC-1 requires. Writing pre-image bytes back is allowed here, because these paths are per-user. Rule (iv) covers shared paths only. The symlink entries among these are handled by Decision 22. Children are removed before their parents.
    - Printing. Undo prints every path that it leaves in place, with the reason, for example "pre-image present", "shared, used by another record" or "ENOTEMPTY". The T3.5 test asserts that list. The new rules add reasons: a supervise directory that holds another name, a link that points elsewhere, a pre-existing `dir`, a foreign subordinate ID line, and an `/etc/ginn` that holds another name.
16. Write rules (F8a, extended by D9).
    - The first creation of `etc/ginn` goes through a temporary directory. Setup creates `etc/.ginn.ginn-tmp`, writes `shared.json` and the pending per-user record into it, and renames it to `etc/ginn`. A crash before the rename leaves only the temporary directory, and creation puts no record in it. Decision 25 uses the same name for its removal, and that directory can hold the records of a finished undo. Setup's sweep and undo's not-configured path both remove a leftover `etc/.ginn.ginn-tmp` under the lock.
    - Setup writes use fixed temporary names, `.<name>.ginn-tmp`, in the target directory. A run removes any stale ones under the lock (Decision 11) before its first write.
    - Post-images carry the mode as well as the digest (Decision 13).
    - Every parent directory that setup writes into must be owned by uid 0 and must not be group- or other-writable. Setup checks each such parent before its first write, and refuses with GINN-E-SETUP-PATH-UNSAFE if one fails the check.
    - `ensure_exact` accepts a same-name line that covers the recorded range. A line covers the range when its start is at or below the recorded start and its end is at or above the recorded end. Setup then appends nothing.
    - `ensure_single` uses the one-line rule. FR-001 AC-1 needs one range of at least 524,288 IDs in each file, so two half-size lines do not count together, and setup adds a third, full-size line. T3.6 doctor uses the same rule.
17. Shared record (D9). One record, `/etc/ginn/shared.json`, serves every user. It is mode 0600, it is schema 4, and it has a top-level `kind` marker.
    - The first setup writes it inside the temporary directory of Decision 16, in the same rename that creates `/etc/ginn`. It exists exactly when `/etc/ginn` does, except in the window after an interrupted undo, which the Residuals describe.
    - It holds every shared entry, in two lists and in the subordinate ID originals. `paths` holds the shared directories that a setup created, each with pre-image `absent`, and the record's own file. `service_paths` holds the shared service-written paths, the root `cgroup.subtree_control`, `sys/fs/cgroup/ginn` and `run/ginn`, each with its pre-image, whether or not it existed before. It also holds the original `/etc/subuid` and `/etc/subgid` (Decision 23), and no other subordinate ID entry. Its top-level keys are `schema`, `kind`, `timestamp`, `boot_id`, `paths` and `service_paths`, and the list of subordinate ID originals of Decision 23, under a key that F11 names. The `timestamp` is that of the first setup, because a later setup changes only the lists. It has no `status`, because it is never pending. It has its own top-level `boot_id` (Decision 12). It lists itself with pre-image `absent` and post-image `self`, as Decision 9 does for the per-user record. No other entry has a post-image (Decision 18).
    - A later user's setup leaves `shared.json` alone, except that it adds a shared directory that it had to create. It never changes the subordinate ID originals. The entry carries that directory's true pre-image, and the entry is added only when the path is not yet in `shared.json`.
    - If `shared.json` is missing while a per-user record exists, setup refuses with GINN-E-SETUP-PATH-UNSAFE and does not recreate it. The refusal happens before the first write.
    - The reason for this record is an order problem. The earlier framing kept the shared pre-images in the first user's record only. Per-user records lost the shared pre-images when users were undone in a different order than they were set up (eighth review MJ1). This record holds them once, for all users.
18. Shared record without post-images (F10, deviation a). `shared.json` is written once, by the first setup. Afterwards it changes only when a later setup adds a shared directory (Decision 17). Its entries carry pre-images only, and the self entry keeps post-image `self` (Decision 9). Completing it with post-images would mean rewriting it after the host writes, which adds a crash window. Undo needs only the pre-images of shared paths (Decision 15). A consequence follows. A rerun does not check the mode of a shared directory, such as `/etc/sv` or `/etc/ginn`, because the idempotence check of Decision 4 reads the per-user entries only. The doctor (T3.6) checks the modes of the shared directories instead.
19. Refusal remedy (F10, deviation b). The remedy of GINN-E-SETUP-PATH-UNSAFE in the error catalogue is one general text. It says to inspect the path with `ls -ld` and `readlink -f`, to keep a copy of a Host Setup Record before any change, to correct a system path in place by hand, and to run host setup again. Case-specific guidance goes in the reason, for example the mode to correct, the uid that must own a path, or the chain that leaves the root. Two refusals with different reasons therefore carry the same remedy.
20. Existing `etc/ginn` without records (F10, deviation c). An `etc/ginn` that exists with no per-user record and no `shared.json` is treated as a first setup. Setup writes `shared.json` into the directory and does not record `etc/ginn`, because the directory was present before the run and setup did not create it (Decision 17: `paths` lists only the directories that setup creates). Undo leaves the directory in place and reports it, because Decision 25 removes `/etc/ginn` only when `shared.json` lists it with pre-image absent. The subordinate ID originals that this setup records are the files as this run finds them (Decision 23).
21. Supervise convention (F11). On Void, runsv creates a `supervise/` directory in each service directory and in its `log/` directory, and that directory holds runit's control state. Most Void services make `supervise` a symlink into `/run/runit`, so the state lives in tmpfs. This was checked read-only on the reference host on 2026-10-12: 80 of the 89 service directories under `/etc/sv` hold such a link, 4 hold a real `supervise` directory, and 5 have none. Host Setup follows the convention. It writes two per-user symlinks, `/etc/sv/ginn-<user>/supervise -> /run/runit/supervise.ginn-<user>` and `/etc/sv/ginn-<user>/log/supervise -> /run/runit/supervise.ginn-<user>-log`. Both links are setup-written and sit in `paths`, each as a symlink entry with its pre-image. The two targets are per-user service paths with pre-image `absent`, held in `service_paths` (Decision 3), because they appear when the service starts. `/run/runit` itself is shared and is not recorded. T3.6 doctor checks that it exists (Decision 14). The reason is the leftover that T3.5 as committed produced. Its runsv state sat under `/etc/sv/ginn-<user>`, and no record named it. T3.5 left `/etc/sv/ginn-<user>` behind on every real Void host (ninth review MJ1), and a second setup cycle then left it unreported. With the links, the state sits under `/run/runit`, and the record names it, so undo can remove it. FR-081 requires the entry to be visible to runit's own status tools (AC-1), and the links keep the entry in the layout runit uses.
22. Undo of the symlinks (F11). Undo handles symlink entries in two places. Step 1 of Decision 15 (v) undoes only the service link, in the resolved runsvdir directory. Each other symlink entry, which means the two supervise links, is undone in step 3 (vi), and each is checked against the target recorded for that entry. A link whose pre-image is absent is removed only while it still points at its recorded target. A link whose pre-image was a symlink has its target restored. A link that points elsewhere is left in place and reported.

The supervise links stay in place through the runsv wait in step 2, because the waiter opens `supervise/ok` through them. The waiter's open is write-only and nonblocking, and it fails with ENXIO when nothing reads the FIFO. The links and the two `/run/runit/supervise.ginn-<user>{,-log}` directories are removed in step 3, after the wait confirms that runsv has exited. A runit directory is removed only when its pre-image is absent and it holds only runit's own names: `control`, `lock`, `ok`, `pid`, `stat` and `status`. Any other name stays, and undo reports it. A regular file at `supervise/ok` is an error. `ok` is a FIFO, which `sv` relies on, so undo reports the error and leaves the directory in place.

A pre-existing `/etc/sv/ginn-<user>` directory is recorded with pre-image `dir`. Undo does not remove it, and it reports it. The next setup finds a directory left by an earlier cycle in this state.
23. Subordinate ID originals (F11). This reverses the rule in Decision 17 that `shared.json` holds no subordinate ID entry. The first setup, the one that writes `shared.json`, records the originals of `/etc/subuid` and `/etc/subgid`. Each original is either absent or stored as its bytes and mode, as a pre-image. Decision 18 holds: there are no post-images. Only the first setup sees the true originals. A later setup does not change them, and a setup that takes the path of Decision 20 records the files as that run finds them. The key name and layout belong to F11, because the committed code has no such key yet. This decision fixes the content and the rules.

Two pre-images answer two questions. The own record's pre-image of a subordinate ID file answers rule (i) of Decision 15: is this exact line ours to remove? The `shared.json` original answers a question only at the last undo. Undo deletes the file only when the original was absent and the file now holds no line. Otherwise undo reports each line that is present now and absent from the original, as a foreign line. The stored bytes are never written back (Decision 15 (i)).

A non-last undo reports each subordinate ID file once, as shared and used by another record. The reason is the ninth review (m1 and m2). Deleting an admin's empty file and missing a foreign line both depended on undo order. With the original in `shared.json`, the last undo decides the same way whichever user was set up first.
24. Record is the identity (F11). Schema 4 adds `home` to the per-user record, next to the uid and gid. Undo takes uid, gid and home from the record, and never from the current account. If an account of the recorded name now has another uid, gid or home, undo prints a warning and continues with the recorded values. A deleted account does not stop undo, because undo needs no account lookup. The realm check (GINN-E-UNDO-REALMS-EXIST, FR-003 AC-2) and the realm walk of Decision 26 use the recorded home. Both records are schema 4 (Decision 13). The reason is that a recycled uid could make undo of one user remove another user's `/run/ginn/<uid>` and cgroup directories. A deleted account's record could also never be undone, and it blocked every other user from being "last".
25. Removal of `/etc/ginn` (F11). For the last record, undo removes `/etc/ginn` in one rename when that is safe, and by the fallback path otherwise. In the rename path, undo renames `/etc/ginn` to `/etc/.ginn.ginn-tmp` and fsyncs `/etc`. It then empties the temporary directory, `shared.json` first and the own record last, and removes it. The rename is taken only when both of these hold. `shared.json` lists `/etc/ginn` with pre-image `absent` (Decision 20). `/etc/ginn` holds exactly `shared.json`, the own record and the fixed temporary names of Decision 16. The rename comes after the host changes of steps 3 and 4 of Decision 15 (v), while the records are still inside. A crash after the rename leaves the temporary directory, which holds the records of an undo whose host changes are already applied. The next setup's sweep or undo's not-configured path removes it under the lock (Decision 16). The fallback path applies when either condition fails. Undo then removes `shared.json`, then the own record, and leaves `/etc/ginn` in place and reports it. Setup's first creation and this removal use the same temporary name, `/etc/.ginn.ginn-tmp`.
26. Remedy and helpers (F11). The remedy of GINN-E-UNDO-SERVICE-RUNNING (exit 75) is three steps, in this order: `sv force-stop /etc/sv/ginn-<user>`, then `sv exit /etc/sv/ginn-<user>`, then a rerun of undo. GINN-E-UNDO-SERVICE-RUNNING is ginn-defined, and `docs/errors.md` lists it. The undo realm walk opens from the recorded home with `O_NOFOLLOW` (Decision 24), and an `OSError` from that walk is reported as a catalogue error. The helpers that setup and undo share live in `hostsetup/_common.py`.

## Alternatives considered

- Write the record after the writes. Rejected: a crash between a write and the record leaves a host change with no record of it.
- Capture pre-images again on resume. Rejected: the crashed run's content would become the pre-image, and undo would restore the wrong state.
- Compare digests of `/etc/subuid` and `/etc/subgid` as well. Rejected: a second user's setup changes those files, so the first user's rerun would report drift and rewrite its record.
- Pick a new range when the recorded one is taken. Rejected by the task design. The range belongs to the user's record, and a silent new range would leave the old one allocated to nobody.
- Call `delegate_user_tree` from setup. Rejected for T3.4, as Decision 8 explains. Undo for those paths is set by Decision 15.
- Lock the whole setup run per user. Rejected: the shared paths are not per user. Not added in T3.4. F8a adds one global lock (Decision 11).
- Create the lock file on the already-configured path. Rejected: a new file in `/run/lock` would break FR-002 AC-1, which requires no host change on a rerun.
- Restore `/etc/subuid` and `/etc/subgid` as whole files. Rejected: a later user's line would be lost.
- Write the pre-image bytes back to root `cgroup.subtree_control`. Rejected: cgroupfs does not accept them (Decision 15, ii).
- Follow symlinks wherever they occur. Rejected: setup follows only the Void chain at `var/service` (Decision 10).
- Keep the shared pre-images in the first user's record only. Rejected: an undo of users in a different order than their setup discards them (eighth review MJ1). Decision 17 holds them in one shared record.
- Let runsv create `supervise/` as a real directory under `/etc/sv/ginn-<user>`. Rejected: its state sits in no record, and T3.5 as committed left `/etc/sv/ginn-<user>` behind on every real Void host (ninth review MJ1). The links keep that state in tmpfs under a name the record holds (Decision 21).
- Decide the subordinate ID files from each user's own record alone. Rejected: the own record cannot say whether a file existed before the first setup, and the result depended on undo order (ninth review m1 and m2). Decision 23 keeps the originals in `shared.json`.
- Take uid, gid and home from the current account at undo. Rejected: a recycled uid could make undo of one user remove another user's `/run/ginn/<uid>` and cgroup directories, and a deleted account's record could never be undone (Decision 24).
- Remove `/etc/ginn` file by file, then `rmdir` it. Rejected: an interrupt leaves an empty `/etc/ginn` with no record, which is window (b) of the Residuals. The rename of Decision 25 leaves no such state.

## Consequences

- T3.5 undo follows Decision 15. It must not restore the pre-image of `cgroup.subtree_control` by writing bytes, and it must not assume the original value (ADR-003). ADR-003 now defers to Decision 15, by its amendment of 2026-10-12 (D9).
- Undo must remove the created files and directories listed in `paths` and in `shared.json`, within the limits of Decision 15, and treat each `service_paths` entry as possibly absent.
- Undo must not restore the pre-image of `/etc/subuid` or `/etc/subgid`. A later user's line would be lost. Undo removes that user's own exact lines from those files instead (Decision 15, i).
- FR-003 AC-1 ("restored to its pre-setup content or removed") is met for the subid files and the shared paths by reversing setup's change, not by writing bytes back (Decision 15, i and iv). That is a reading of the SRS wording, not the wording itself, and CL-11 records the gap. Removing the line setup appended, and disabling the controllers that the run script added, return each path to its pre-setup state, except where CL-11 says undo leaves a path in place. No bytes are written back, because other users' lines and live cgroup state may have changed since setup.
- The per-user record can be complete only with subordinate ID ranges and a post-image for every per-user setup path. `hostsetup/record.py` refuses to write any other record, and refuses to read a record that breaks these rules. It applies the same refusal to `shared.json` (Decision 17).
- A record that exists but cannot be read is refused with GINN-E-SETUP-PATH-UNSAFE (exit 77). That applies to `shared.json` too. It is never treated as absent, because that would capture pre-images from a host that setup already changed.
- The install split of `runit_system.py` (`install`, `install_scripts`, `install_link`) is removed by F9b. Setup writes the output of `render()` itself, under Decisions 1 and 16.
- The service-written paths are the six of Decision 12 and the two runit directories of Decision 21. Five are per-user (`ginn/<uid>`, `ginn/<uid>/supervisor`, `/run/ginn/<uid>`, and the two runit directories), and they sit in the per-user record. Three are shared (`/sys/fs/cgroup/ginn`, `/run/ginn`, and the root `cgroup.subtree_control`), and they sit in `shared.json`. T3.5 covers all eight.
- Doctor reads host state, not the record (Decision 14), so a damaged record cannot hide a host fault from `ginn doctor`.
- Undo reads uid, gid and home from the record (Decision 24). A deleted account can be undone without an account lookup.
- In the normal case `/etc/ginn` leaves in one rename (Decision 25), so the records are the last host-side items that undo removes.

## Residuals

- Crash in the record's directory window. Closed by Decision 16 for creation, and by Decision 25 for removal. A crash before the rename leaves the temporary directory and no other write. A creation leaves no record in it. A removal can leave the records of a finished undo. The next run removes it under the lock.
- Controllers enabled after the pre-image. Undo (ii) cannot tell a controller that the run script added from one that another party enabled after the pre-image, within the same boot. The record keeps no post-image for that path. Undo accepts this limit.
- Reclaim gate. A stale subordinate ID lock is reclaimed through `/run/lock/ginn-<file>.lock.reclaim`, which is written only in that case and then stays. It is not recorded. It is an empty file in a tmpfs that a reboot clears.
- Concurrency. Closed for setup and undo by Decision 11. The subordinate ID lock still covers only the append.
- Lock file. `/run/lock/ginn-host-setup.lock` stays after a run, as an empty file in tmpfs (Decision 11).
- Interrupted undo, window (a), narrowed. On the rename path of Decision 25, `shared.json` and the own record leave `/etc/ginn` together, so a crash cannot leave one without the other there. The fallback path still removes `shared.json` before the own record, and an interrupt between them leaves a per-user record without `shared.json`. The next undo finishes the work, and it skips the shared steps, because they were applied before `shared.json` was removed. Setup refuses in this state (Decision 17) and names undo as the way out.
- Interrupted undo, window (b), closed for a directory that setup created. Undo leaves `/etc/ginn` by one rename (Decision 25), so an interrupt leaves the temporary directory and never an empty `/etc/ginn`. The fallback path leaves `/etc/ginn` with another name in it, so it is not empty. A directory that setup did not create (Decision 20) stays in place by design, and undo reports it. That is the case in which `/etc/ginn` exists without `shared.json`. The next setup treats it as a shared directory with pre-image present, and it writes `shared.json` into it.
- Racer and `/run/lock`. A run that loses the lock and then finds "already configured" may have created `/run/lock`, and no record names it. Void always has `/run/lock` on tmpfs, so the case should not arise there. Undo does not remove it.
- Crash before the first record, with `/run/lock` missing (F10, deviation d). `_global_lock` creates a missing `/run` or `/run/lock` before any record exists. It does not parent-check either directory, and it opens the lock file without a parent check. A SIGKILL after that and before the temporary-directory rename (Decision 16) leaves the directory on disk, with no record that names it. The next run finds it present, so it does not record it, and undo does not remove it. Void ships `/run/lock` as a root-owned tmpfs, so on Void both directories exist from boot and nothing is created.
- Wait checks only runsv. Undo's wait (step 2 of Decision 15 (v)) confirms that runsv has exited, through `supervise/ok`. It does not check that the service's cgroup is empty. A `populated 0` check on the cgroup is a possible later hardening.
- Real-host proof of FR-003. `tests/integration/test_runsv_real.py` (`GINN_INTEGRATION=1`, no root) proves the supervise links and the waiter against the real runsv. FR-003 is fully proven only by a real host round trip: `sudo ginn host-setup --user <user>`, then `--undo`, with before and after snapshots. That needs the user's approval, and it has not run.
- Name collision, not detected. Void names a runit directory `supervise.<service>`. The user `foo-log` maps its main supervise directory to `/run/runit/supervise.ginn-foo-log`, and the user `foo` maps its log directory to the same path. Setup and the classifier do not detect this, and Decision 21 does not address it.
- Schema 3 hosts. A host with a schema 3 record from before F11 is refused by setup and undo, with the reason "written by a build before F11". This ADR gives no manual way to clear such a record. Check for one with `ls -l /etc/ginn` on any host that ran setup under F9a or later, and decide the case before F11 runs there.
